2 · The pipeline as it runs today

Per row, Stage 3 does the following, cheapest first; every API answer is cached under content-complete keys (prompt version, every model the call can reach, and the rendered inputs), successful verdicts and declines are cached, transport failures never are.

  • Front-door screen. Two models from different lineages (gemini-3.5-flash-lite + ministral-14b-2512) each answer "is this a replication or reproduction at all?". Agreed no → discarded to not_a_replication.csv; split → screen_disagreement.csv; one or zero answers → the row waits (target_pending / api_error) rather than being mis-filed. Only survivors pay for anything below.
  • Match-type routing. Multi-original papers are detected by deterministic rules plus an LLM call that fires only when the abstract carries ≥2 distinct author-year pairs.
  • Resolution ladder. Title patterns → citation rules → abstract LLM over a bounded candidate list → reference-list target pick (accepted only at high confidence) → title search (high-confidence screens only, always provisional) → PDF + full-text LLM. Self-links are rejected, and a rejected link also clears any outcome that was attached to it.
  • DOI verification. Every written doi_o is checked against CrossRef/OpenAlex metadata; mismatches are re-resolved strictest-first or downgraded, never silently kept.
  • Outcome coding, only on resolved links. The abstract is read first; if it cannot settle the outcome, the escalation reads the paper's discussion/conclusion (head and tail of over-long discussions both survive truncation). Multi-original papers are coded one row per original paper, study numbers joined in study_o, outcomes aggregated by FLoRA's mixed-if-conflicting rule.
  • Quarantine. sanity_check runs at the end of every extraction (including Ctrl-C) and routes problem rows to per-reason review files; --resume treats those files as settled decisions unless --rescreen is passed.

csv_to_db pushes resolved rows to Supabase — blocked every insert fails until the validation repo adds title_r/title_o columns (issue #103). Nothing is written or corrupted in the meantime.

3 · How far to trust it

  • Code: 732 tests pass (one pre-existing failure from a missing local data file, unrelated); three independent adversarial reviews of the riskiest code paths ran this week, and every confirmed finding is fixed and re-reviewed. No known open correctness defect.
  • The screen: the current voter pair was chosen from all 28 pairings of 8 models and validated against hand-coded cases: 21 of 22 hand-checked discards were genuine negatives — the one miss is an instrument-revalidation case, a systematic gap the proposed prompt in §5 addresses. The panel-based comparison numbers (e.g. "89% vs 25% correct discards") are indicative only: the LLM adjudication panel disagreed with the human coder on 4 of 15 calibration cases.
  • The ground truth itself: 75 hand-coded cases exist (flora_coding_75_results.csv plus adjudication files) — currently only in untracked scratch_* files. They are derivation data for the current design, so future evaluations must hold them out or cross-validate.
  • Known soft spots, unchanged: Stage-2 precision (an estimated 47–58% of what reaches Stage 3 is not a replication — every downstream call is multiplied by this); the 1,151 legacy-linked rows in extracted.csv whose links predate all current validation; parse-method scoring (issue #43); multi-original identification quality (issue #12).

8.1 · The front-door screening prompt

This is the deliverable of the hand-coding round, ready to implement and evaluate (step 4 of the sequence above). It replaces the production classification prompt for the front-door screen. The rules it encodes: an explicit intent bar (checking an earlier finding must be an aim of the paper — framed as excluding clearly incidental re-tests, since centrality cannot be coded reliably from abstracts), the settled instrument-validation rule (only initial validation is excluded — re-validating a published instrument, including in a new language, counts), enumerated distractor senses of "replication", and a target-specificity clause (the target must be a particular reported finding, not established background knowledge). The output classifies each paper as replication | reproduction | both | none | unclear — replications and reproductions are distinguished at the screen, not downstream — and names every pattern it fits in a categories array (multi-select, so a declared self-retest carries both tags; evidence quotes may come from the title as well as the abstract). The task and full output schema, including a valid example JSON object, are stated before the rules. This prompt was written fresh from a written task specification (scratch_screen_spec.md) rather than by editing the production prompt, then revised against an independent codex review focused on clarity for small models.

You are screening papers for a database of replication and reproduction studies.

You will be given one paper's title and abstract. Decide whether that paper is the kind of study the database collects.

Return one valid JSON object only. Include the required "reasoning" field inside the object, but add no prose, commentary, markdown, or code fences outside it.

Return exactly five fields:

- "classification": one of "replication", "reproduction", "both", "none", or "unclear"
- "confident": true or false
- "categories": a JSON array of one or more values from the category list below
- "evidence_quote": a short exact quote from the title or abstract, or ""
- "reasoning": one sentence

Field meanings:

- "classification" — what the paper is. Use "both" when the paper re-analyses earlier data and also collects new data to re-test the same finding. Use "unclear" when the abstract genuinely does not settle the question either way. Use "none" when the paper does not qualify.
- "confident" — whether you would stake the decision on the abstract as written. Follow the confidence rules below.
- "categories" — every pattern from the list below that describes the paper, in the order they appear in the list. Include at least one.
- "evidence_quote" — a quote copied word for word from the title or abstract that supports the decision. Use "" if no wording supports a quote.
- "reasoning" — one sentence saying why this classification follows.

Category values:

- "clearly_declared" — the authors themselves frame the work as a replication or a reproduction.
- "self_retest" — the authors re-test a finding from their own earlier published study.
- "measurement_validation" — re-validation or re-evaluation of an already published instrument, test or procedure.
- "context_transfer" — the same claim is re-tested in a new population, country, language or setting.
- "incidental_finding" — a re-test is present in the paper but is not one of its aims.
- "initial_validation" — the first validation of a newly proposed instrument.
- "tool_benchmark" — a new method, model or simulation is shown to reproduce known results in order to demonstrate that the tool works.
- "builds_on_literature" — the study tests established background knowledge rather than a particular reported claim.
- "terminology_only" — the vocabulary appears in a biological, ordinary-language or field-specific sense.
- "about_replication" — a review of, or commentary about, replication or the replication crisis.
- "other" — none of the above fits.

Example of the required JSON structure:

{
  "classification": "replication",
  "confident": true,
  "categories": ["clearly_declared", "context_transfer"],
  "evidence_quote": "we conducted a direct replication in a German sample",
  "reasoning": "The authors state that re-testing the original finding in a new population is an aim of the study."
}

STAKES

A confident "none" permanently discards the paper. False discards are costly; false inclusions are cheap, because later stages and human reviewers can still remove them.

You never have to identify which earlier study is being checked. A later stage of the pipeline does that. Your only job is to judge whether this paper is the kind of study the database collects.

WHAT QUALIFIES

A paper qualifies when checking a specific finding from earlier published research is one of its stated aims.

- Code it as "replication" when new data are collected in order to re-test a finding reported in a previously published study.
- Code it as "reproduction" when an earlier study's own data are re-analysed in order to check the result that was reported from them.
- Code it as "both" when the paper re-analyses the earlier data and also collects new data to re-test the same finding.

Each of the following qualifies:

1. Context transfer. Re-testing the same claim in a different population, country, language or setting qualifies.
2. Conceptual replication. Re-testing the claim with a changed method, measure or paradigm qualifies.
3. Self re-test. Authors re-testing their own earlier published finding in a separate paper qualifies.
4. Measurement re-validation. Re-testing, re-validating, translating or adapting an already published instrument, scale, test or clinical procedure qualifies, including when this is done in a new population, language or setting, and including when the stated aim is that instrument's reliability, test-retest, inter-rater agreement or reproducibility in that new population, language or setting.
5. Comment or reply with its own analysis. A comment, reply or letter that presents its own re-analysis of a published result qualifies.
6. Author self-declaration. If the authors explicitly identify the study itself as a replication or reproduction, accept that framing and use the type they declare. Merely using related vocabulary in one of the non-qualifying senses below is not a self-declaration. Author self-declaration applies only when the declared target is earlier published research in another paper; a declared "replication" whose target is elsewhere in this same paper is an internal replication.

WHAT DOES NOT QUALIFY

Return "none" in these situations.

- Declared intent. The paper must set out to replicate, reproduce or otherwise check the earlier finding — the check must be something the paper aims to do. Return "none" when the abstract presents the agreement or re-test as an incidental result or interpretive remark rather than an aim of the paper.
- Target specificity. The thing being checked must be a particular finding that someone reported, not the accepted background knowledge of a field. A study that tests whether something the literature already widely holds applies in its own sample is ordinary research building on prior work. Example of accepted background knowledge: "the well-established association between X and Y". The abstract does not have to name the source study: a paper qualifies if it clearly aims to check a particular finding reported by earlier research.
- First validation of a new instrument. The initial validation of a newly proposed instrument does not qualify, because there is no earlier reported finding to check. By contrast, re-validating an already published instrument qualifies.
- Comment without analysis. A comment or letter that only argues about an earlier study, presenting no new data and no re-analysis, does not qualify.
- Internal replication. A re-test of a result obtained elsewhere in this same paper, thesis or dissertation does not qualify, whatever the authors call it — "Study 6 was a replication of Study 2", "two experiments that are a replication of one another", or a second objective that replicates a pattern the paper itself has just reported. The target must be earlier published research in some paper other than this one. This covers the two-stage discovery design: a study that identifies a signal in its own discovery sample and then confirms it in its own second sample does not qualify, however that second sample is labelled. "Replication set", "replication sample", "replication cohort", "stage 2" and "confirmed in an independent cohort" describe a design internal to the paper, not a check on another paper's finding. It qualifies only if the abstract says the association being confirmed was reported by earlier research.

The words "replication", "reproduce", "reproducibility" and their relatives are used in several senses that do not qualify:

1. Technical or measurement precision that does not concern an already published instrument's properties — sample-to-sample precision, device-to-device precision, inter-rater or intra-rater agreement computed as part of this study's own methods, and multi-laboratory round-robin, ring-trial or proficiency-testing exercises run as laboratory quality assurance. The aim of these studies is to quantify the spread of a measurement, not to check a property earlier research reported. Reliability, test-retest, inter-rater or reproducibility work on an already published instrument, scale, test or procedure is rule 4 above and qualifies.
2. Tool benchmarking: a new model, simulation, numerical method, assay or apparatus demonstrated to reproduce known results in order to show that the tool works. This holds even when the abstract names the published results the tool recovers, and even when it uses the words "reproduce", "replicate", "verify" or "validate against" — recovering what earlier work reported is a property of the tool, and the tool is the paper's subject. Exception: a study whose aim is to settle whether the earlier claim itself holds, including a re-analysis of the earlier study's own data, qualifies.
3. Ordinary-language, biological and field-specific senses: DNA, viral, cell or histological replication; "replication" as a count of overlapping samples in a chronology; "replicated across sites" describing the internal design of the study being reported; reuse of an earlier paper's framework, element list or protocol as this study's instrument ("using 16 elements of X's research"); and rolling an engineering solution, pilot or intervention out to a further site.
4. Papers about replication: reviews, commentary on the replication crisis, or a paper that merely states that future replication is needed.

CONFIDENCE

Apply both the qualifying rules and the exclusion rules. If the abstract supports more than one reading, use the rules below; do not resolve ambiguity by defaulting to "none".

- Answer "confident": true only when the abstract states plainly what the paper set out to do, so that the rules above settle the case on the wording in front of you.
- Answer "confident": false when your answer rests on inference, when the abstract is vague about the paper's aims, or when a different reading of the same sentences would change your answer. Both values are ordinary answers: a "none" you are not confident in still means "none", and it means the paper will be looked at rather than dropped. Saying false when you are unsure is the behaviour this field is for.
- Be confident about "none" only when the abstract clearly describes a purpose that does not qualify, for example an unambiguous instance of one of the non-qualifying senses of the vocabulary, a first validation of a new instrument, or a plainly incidental agreement with prior work.
- An abstract that describes checking a specific reported finding but does not name the source study is not grounds for a confident "none". Classify such a paper as qualifying and leave identification of the source to the later stage.
- When the abstract genuinely does not settle the question in either direction, use "unclear" rather than forcing "none".

Judge only from the title and abstract below. Do not speculate about content the abstract does not contain.

Title: {title}

Abstract: {abstract}

Respond with the JSON object only.

The categories field (multi-select over the 11-value list in the JSON above, stored joined with | in the CSV) is carried from the screen into extracted.csv and the validation DB as a new per-row column, written the same way the existing classify_llm_model column is (that column records which model classified original_match_type; this one records which patterns the screen saw). It buys three things: evaluation questions become queries ("how does the screen do on measurement validations?") instead of hand-coding exercises; the discard path becomes monitorable by category; and when a coding rule changes, the re-adjudication sweep is a filter over the corpus, not a re-audit. 8.2 · The target-identification prompt — one prompt for the whole ladder

Three prompts in the resolution path ask one question over different evidence: build_match_type_prompt asks how many originals a paper targets, build_target_prompt asks which reference is the target, and build_identification_prompt asks which candidate or reference is the target. Merging them into a fixed core plus dynamic evidence blocks leaves one prompt to review and optimise, and collapses items 2, 3 and 5 of the §9.0 triage list into a single review. Draft: scratch_integrated_target_prompt.py, revised twice against codex review.

done Merged (PR #117, 2026-08-01, reworked on top of PR #116's refactored Stage 3): shared/target_keys.py provides the deduplicated @smith2009 key namespace, build_target_prompt serves ladder stages 4, 4.5 and 7 (the old identification and reference-target prompts are deleted), and identify_targets_with_llm enforces match_certain acceptance with every key resolved against the call's own key map. A single-routed row whose resolver saw N targets is rerouted through the multi-original pipeline rather than keeping one link. Per the sequencing above, classify_match_type and multi_original.py are untouched — and the §6.2 review confirms that per-target adapter is now the highest-value piece of remaining work, because the reroute currently re-enters the old multi machinery.

Counting stops being a prediction. The pre-ladder match-type call spends a heavy-model call asking how many originals a paper targets, and the next call names them from the same evidence. The count is contained in the enumerated answer, so the merged prompt returns a targets array and the count is read off it. The saving comes from deleting the match-type call, not from adding an enumeration call ahead of the ladder: the merged prompt runs only where an LLM call already happens, and returns a list where it used to return a scalar. The rows that pay for the match-type call today — the roughly 6% with two or more distinct author-year pairs — drop from two heavy-model calls to one.

Targets are named by BibTeX-style keys (@smith2009) over one namespace spanning the candidate list and the reference list, which is also the §6.1 backlog item asking for explicit keys instead of positional numbers. Two details make the difference between this working and quietly corrupting links. Records are deduplicated before keys are assigned, matching on DOI first and then normalised title and year, so a work that appears both as an OpenAlex candidate and as a parsed reference gets one key — otherwise a collision suffix would advertise a synthetic ambiguity between a paper and itself. And the builder returns the key→record map it used alongside the prompt: keys are assigned per call from whatever records that call had, so the same work can hold a different key at a later stage that supplied more references. Resolving a returned key means looking it up in the map from the call that produced it, never recomputing it from a different list.

Two judgments per target, kept apart — and the acceptance bar survives. Whether the paper re-tests a study is why the entry exists, evidenced by a verbatim evidence_quote. Whether we know which published record that study is, is a separate boolean, match_certain, and that is the acceptance gate. This matters more than it looks: Stage 4.5 today accepts a reference pick only at confidence == "high", and treating "the model returned a key" as sufficient would silently convert every hesitant pick into a resolved link — one that enters RESOLVED_LINK_METHODS, gets outcome-coded, and skips quarantine. _link_confidence() could not restore that bar, because it labels links that have already been accepted. So the vague three-point scale is gone and an explicit, checkable gate replaces it, at least as strict as the one it replaces.

A stated study count is an accounting claim, not a quota. The model reports stated_count, what it counts in stated_count_unit (papers, studies, findings, experiments, sites, unclear), the words it appears in, and how many targets it could not identify at all in unidentified_count. The caller then checks the arithmetic rather than trusting it. Both halves are load-bearing: without the shortfall counter a paper that replicates 28 studies can silently report three, and without the unit a demand for 28 entries conflicts with the prompt's own rule that several studies from one paper are one entry. The prompt says in terms that the count never licenses inventing a target.

Ordering and evidence. Static instructions and the response schema come first, per-row inputs last, for prefix caching and instruction adherence; the paper's own text precedes the lists; and a reviewer's note is placed with the inputs rather than ahead of the instructions, since it is per-row data and putting it first would both break the cacheable prefix and give reviewer text priority over the task. The abstract budget goes from 700 to 3,000 characters — 700 cut a standard 350-word abstract in half, and the target is usually named in the second half. The reference list is sent uncapped, as production's identification prompt already does, because the one thing a truncated list can do is make a genuine target unmatchable. The PDF-extracted abstract is sent for what it adds: when the OpenAlex abstract is a truncated prefix of it, the tail is included and the duplicated head dropped, which is precisely the passage that motivated the larger budget in the first place.

Nothing is trusted without checking. Once acceptance no longer rests on a self-reported confidence, the cheap validations become the guard: a returned key must exist in that call's map, no key may appear twice, evidence_quote should be findable in the text actually sent, and unidentified_count must be a non-negative integer that reconciles with stated_count when the unit is comparable. A fabricated quote or an invented key would otherwise land in the database as a resolved link.

_MULTI_TITLE_RE is deleted on evidence. It fires on "many labs" and "many analysts", but Many Labs 4 replicated one original across many laboratories and a many-analysts paper is many teams re-analysing one dataset — the rule asserts multiple_original for single-target papers. The count regexes survive in one narrower job. run_for_doi() is a first-success ladder, so a multi-target paper with one conspicuous target can resolve early and terminate before anything enumerates the rest; the replacement for the router is a may-not-short-circuit gate — a row may stop at a deterministic stage only when title and abstract carry exactly one distinct author-year pair and no study count was found. No rule asserts multiple_original any more; a rule can only withhold the cheap path. A false positive costs one LLM call, a false negative silently drops 27 originals.

What this needs before it can ship, and what it does not yet have. The gate above narrows the first-success exposure but does not close it: one cited author-year does not prove that no uncited, group-authored or title-named second target exists, so this needs measuring against the corpus's known multi-target papers. More substantially, the per-target routing is a specification, not something today's code can express — no current caller consumes targets, the multi-original writer stamps one link method across all originals rather than deciding per target, unidentified_count has no column to live in, and provisional targets have no doi_o from which to derive a stable pair_id. Until an adapter exists that produces one record per target with its own resolved-or-provisional status, classify_match_type() stays. The merged prompt can be reviewed and evaluated first; the router is deleted last.

8.3 · The outcome prompts — four collapse to two

done Merged (PR #118, 2026-08-01) exactly as specified below — see the §8.3.1 status note for the two follow-ups (legacy reproduction recode, the receiving-side Supabase migration). The prose below is kept as the design rationale; "today" in it means pre-#118.

Outcome coding runs four prompt builders today: build_outcome_abstract_prompt, build_outcome_fulltext_prompt, build_repro_abstract_prompt and build_repro_fulltext_prompt — a 2×2 grid over two questions (which vocabulary: replication or reproduction) and two passes (abstract-only, or the full-text escalation that fires when the abstract cannot settle it). Only one of those two axes justifies a separate prompt. The vocabularies are genuinely different documents: one codes a verdict on a finding, the other codes two axes of a re-analysis. The passes differ by a handful of lines — which evidence is present and which quote sources are legal — and those lines were being maintained as two divergent copies of a two-hundred-line rule block. Below, the pass becomes a parameter and the four builders become two.

The evidence is described, not encoded. The pass is not announced with a marker for the model to interpret; the builder simply writes what the model is holding ("You have the paper's title and abstract" versus "…and a passage of the paper's full text") and omits the full-text block entirely when there is none. Quote-source legality follows from that sentence. Both variants are constant within a pass, so cross-row prefix caching is unaffected.

is_genuine_attempt is retired from the abstract pass, and replaced on the full-text pass. Every row that reaches outcome coding has already passed the front-door screen (run_extract.py:1688): two voters, validated against hand-coded cases, on title and abstract. On the abstract pass the outcome LLM sees exactly that evidence again — so its genuineness verdict is one model re-deciding a validated two-model question, and because _normalise() turns a false into outcome = not_a_replication, which is terminal and never escalates, that single model can end the row. The full-text pass is different in kind: it is the first call in the pipeline to see the methods. So the field is dropped on the abstract pass and replaced there by record_type_check (replication | reproduction | neither | unclear). neither carries the veto, now earned by evidence the screen never had; and an answer naming the other vocabulary is the more valuable signal, because record_type will come from the screen (§8.1.1, item 5), which cannot see whether a paper re-analysed the original's data. That row is re-coded once in the right vocabulary rather than silently coded in the wrong one.

The reproduction grid becomes 4×3 in two fields. Following the §5 decision and the codebook update that went with it, outcome_computation takes computationally reproducible · computational issues · technical failure · not checked, and outcome_robustness takes robust · robustness challenges · not checked, each with cannot_be_determined as its own escape and each carrying its own quote and quote source (outcome_computational_quote / out_quote_computational_source, outcome_robustness_quote / out_quote_robust_source). That closes audit findings R1 and R2 together: a validator no longer sees one quote asked to justify two independent judgments, and no downstream analysis has to re-split a joined string to read one axis.

technical failure is the value that changes the most rows. It is the case where the reproduction was defeated by the materials — no data, no code, an unrunnable workflow — which is the most common real reproduction outcome in economics and had no representation at all in the 3×3 grid. Without it, such a paper had to be recorded either as computational issues, asserting a numerical disagreement that was never observed, or as cannot_be_determined, asserting that we could not read the paper. Because the new value sits next to three others that all sound like failure, axis 1 is written as an ordered decision tree, and the boundary is made concrete: did comparable numerical output exist at all? If it did and disagreed, that is computational issues; if it never did, that is technical failure. The codebook also settles a question the drafting raised — "we only care about numbers and rounding; as long as the same numbers appeared (regardless of what it took)" — so a reproduction that needed a corrected script or a note to the authors before the numbers came out is still computationally reproducible, not an issue.

not checked is read off what the paper did, not only off what it says. The draft treated it as a claim needing an explicit statement, with silence falling to cannot_be_determined. That is too strict in the common case: a paper reporting only alternative specifications has told you it did not set out to reproduce the original numbers, without ever saying so. Both axes now accept that inference — a not checked verdict may rest on what the paper describes doing — while cannot_be_determined keeps the cases where the paper says too little to tell what it did. The axis-2 wording goes further and names the pattern outright, because it is the one that recurs: the paper considered robustness only, or reproducibility only.

Two axes make escalation a per-axis question. Today _llm_outcome() escalates when the single joined outcome comes back cannot_be_determined. With two fields it must escalate when either axis is unresolved, and the escalation call re-codes both from the fuller evidence rather than patching one in. A settled computation verdict beside an unresolved robustness verdict is the common case, and treating it as settled would silently record "not checked" as though the paper had been read to the end.

An unresolved abstract verdict is not cheap. The first draft told the model that cannot_be_determined merely bought a second look. For many papers no PDF can be acquired, so the abstract verdict is the only reading the paper ever gets. Neither prompt now says anything about what happens next — pipeline mechanics are not something the model can act on — and both state the two failure modes side by side instead: do not guess an outcome the evidence does not support, and do not withhold one it does state, or strongly imply with a sentence that can be quoted.

Multi-original papers use these same two prompts, once per target. Today they take a third route — build_multi_original_prompt identifies every target and codes a per-target outcome in one call, after which _collapse_same_paper_originals() merges studies belonging to one original paper and _aggregate_outcomes() applies FLoRA's mixed-if-conflicting rule (run_extract.py:916). That makes the least-reviewed wording the one handling the hardest papers. The outcome half of that prompt is deleted and each confirmed target is coded by the prompt below, its target block naming the original this call is about. The aggregation rule stays in code for several studies from one original paper, and is now also stated in the prompt so the model's own verdict agrees with it. The cost is N calls where there was one, which is currently free: extracted.csv contains no rows with n_originals > 1, so nothing in production is re-coded by this change.

Smaller changes carried through both drafts. Static instructions and the response schema come first and per-row inputs last, for prefix caching and instruction adherence (the §6.1 all-prompts item). The genuine-attempt rule no longer trails the outcome rules — the other §6.1 outcome item. The three-level confidence becomes the binary confident, on the §8.1 finding that the three-level scale was a constant in practice. Quotes are 1-4 complete sentences, the shortest passage that stands on its own, and may span two sections joined by  |  with their sources listed in the same order. Quote provenance is described honestly — the full-text block is whatever the parse waterfall supplied, not reliably "the discussion section". What was a paragraph of JSON discipline is now one line: the prompt polices field names and category spellings, and the parser repairs what a parser should repair ("true" → true, null → "", trailing commas), rather than spending model attention on it.
