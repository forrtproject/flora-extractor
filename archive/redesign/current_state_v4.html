FLoRA Extractor — Current State & Way to Go Live (v4)

The pipeline after the 2026-08-04 end-to-end cleanliness review. Supersedes current_state_v3.html, whose §6 run-plan (rescreen, re-run, import) remains valid and is not restated here — this page covers what the review found, the honest state of the Stage-2 rule book, the pragmatic path to switching rules on, and the refactoring decisions the review surfaced.

In one paragraph. Four independent reviewers (three Claude audits plus a codex second opinion) went over the pipeline end to end. The code is in good shape — the filter engine, per-target adapter and screen survived review with no functional regressions — but the Stage-2 rule book was carrying validation numbers that do not survive scrutiny: the gold corpus behind every large-n claim is 62% unconfirmed old-pipeline LLM output (#151), partly circular with the rules it was used to validate, and no cited evidence artifact exists on main. This pass therefore reverted every statistically-claimed discard rule to draft (shadow), kept the six genuinely structural discards live, stripped the overclaims from the spec texts, deleted the dead code and legacy documentation the audits found, fixed ~60 documentation defects (largely closing #113's classes), and restructured the engine tests so policy lives in one table. The suite is green: 1,062 passed, zero failures. Everything is uncommitted in the working tree, awaiting review.

1 · The pipeline, in one screen

StageCommandWhat it does
1 · searchpython -m search.run_search Searches; it does not filter. The snapshot scanner (snapshot_scan.py) runs the search gate — a vectorised token/stem match plus concept membership, the only affordable predicate over 510M snapshot rows — and every survivor enters the parquet survivor pool, shared via HF (pool_sync.py). No exclusion pattern runs here and nothing gates admission: the stem alternation is the OpenAlex search query, and it is the one deliberate exception to “one rule set”. data/candidates.csv is retired as an admission-gated corpus; the pool is the Stage 1 output.
2 · filter enginepython -m filter.engine route / screen / handoff Declarative JSON specs route the pool into piles by precedence (discard / screen_expensive / screen_cheap / needs_human / pending). Rules route and discard; only LLM tiers admit. Verdicts are claimed and release-bound in the DuckDB/Postgres store; handoff writes Stage 3's input.
3 · extractpython -m extract.run_extract Two-voter front-door screen (v3.3, gate G-softqual) → resolution ladder (cheapest first) → per-target adapter for multi-original papers → outcome coding (two prompts, one per vocabulary; reproductions on the two-axis grid). DOI verification on every written row; sanity_check quarantines to set-aside CSVs.
4 · validatepython -m validate.app Read-only monitoring dashboard; human validation lives in the separate Supabase-backed repo, fed by extract.csv_to_db (blocked on the cross-repo migration, flora-validation#3).

2 · What the review found and changed (all uncommitted, 2026-08-04)

2.1 The validation numbers were not real

Three independent findings, mutually confirming:

  • Compromised gold. Every large-n measured claim (“5.6M rows scored against the 7,505-paper gold corpus”) used override_positives.json, of which 62.4% is the old pipeline's own unconfirmed LLM verdicts (#151) — and that bucket only contains rows the old keyword filter admitted, so the measurement is partly a rule agreeing with its own ancestor. The empirical bite: all 14 non-qualifying papers found in the audited genetics stratum came from the LLM bucket, none from the human-curated strata.
  • Unverifiable hand-checks. deposit-doi-prefixes claimed precision 0.995 on n=282 from a sample (30k-candidates-2026-07) that exists nowhere in the repo or its git history — and 0.995 is not an attainable proportion at n=282. non-article-type's n=50 check measured the wrong estimand (recall of the type signal, not discard precision).
  • No evidence on main. The cited eval reports live only on the unmerged analysis/stage-b-eval branch (which predates the specs it would justify), the gold corpus only in an old worktree. Not one quoted figure is reproducible from any checkout.

2.2 The rule book was reset accordingly

Live autonomous discards are now exactly the rules whose justification is structural — true by construction, needing no sample. Everything with a statistical claim is a draft (shadow: true): it still evaluates and records matches on every run, but never affects a pile. Overclaiming measured text was rewritten honestly everywhere (exact snapshot counts kept; gold-recall figures removed or explicitly disclaimed per #151). New policy in filter/spec/CONVENTIONS.md: a measured entry must record its denominator's provenance, and unstratified override_positives.json figures are not acceptable evidence. Bundle 69dcfa41f2b4; the next route mints a fresh release.

The reverts take effect where it matters: Stage 2 routes the Stage A survivor pool (~5M rows), and _pool_record() pools every Stage A survivor before _row_if_admitted() is consulted, so a shadowed exclusion really does stop affecting which papers the pipeline can reach. Stage 1's keyword_verdict() still applies the patterns, but what it gates is admission into data/candidates.csv — which nothing in filter/ or extract/ reads. That two-evaluator, two-corpus split is analysed in rulebook_review.html §2.1 and is decision D9 below. Test policy now lives in one table (tests/test_engine_spec.py), with a standing invariant that the rescue can never be live while its targets are shadow.

3 · How to get going — first safe rules, then a validation path

The position: the engine can run in production today on the six structural discards plus the routing rules — that configuration deletes only what is true by construction (deposit DOIs, review/decision objects, non-article registry types, molecular-biology terms of art) and routes everything else to the LLM tiers, which are the components that were actually validated (screen v3.3: 0 settled misses at the shipped gate). The cost of the reverts is purely money: rows the technical/dataset rules would have discarded now reach the cheap screen (~$0.001–2/row) instead of dying free. That is the right trade until the discards are honestly measured.

3.1 Prerequisites (one-time, no API cost)

  1. Bring the evidence home. Merge analysis/stage_b_eval/ from the analysis/stage-b-eval branch onto main, and commit override_positives.json (or a pointer + hash if too large) with its provenance table. A spec may only cite evidence a main checkout contains.
  2. Build the honest gold set. Stratify the corpus per #151: the human-curated strata (entry_sheet 1,551 + flora_db 1,266 = 2,817 papers) are the recall benchmark; the 4,681 allrep_llm rows are demoted to “candidate positives”. Grow the negative pools (74 + 14 rows is too small to bound anything).
  3. Construct filter/spec/holdout.json (reserved in the loader, never created): freeze a stratified sample now, before any tuning, so later promotions have an untouched test set.

3.2 The promotion recipe (per draft rule)

  1. Run a routing release; the shadow rule records its matches at zero risk.
  2. python -m filter.engine diagnose <rule> → export the rows the rule would have discarded.
  3. Sample ~100–200 of them, stratified by year/field. Human-code (or LLM-code with the model id recorded) against the FLoRA qualification rule.
  4. Write the result as the spec's measured entry — level, n, date, owner, sample id, and the denominator's provenance, per the new CONVENTIONS.md requirement. The artifact goes in analysis/ on main.
  5. Un-shadow via a reviewed PR whose diff is the spec file + the policy-table line in tests/test_engine_spec.py. Suggested bar: ≥0.98 precision on n≥100 with zero qualifying papers killed, or an explicit maintainer sign-off on the residual.

3.3 Suggested order

  1. dataset-type — cheapest audit (deposit records are obvious at a glance), biggest routing volume, and its pilot already suggests the discards are right; it only ever lacked the sample.
  2. technical-object + technical-verb + title-phrase-rescue — as one bundle (the rescue's scope is the pair). These need the careful audit: the #147 evidence says they were killing real computational reproductions before narrowing; post-narrowing precision is genuinely unknown.
  3. biological-of, data-availability — only after deciding the pyre_regex question (their RE2 decompositions widen the discard; either accept the widening with a measurement or keep them Stage-1-only forever).
  4. nfd-stems, reproduce-verb-arms — routing drafts; promote whenever their diagnose output looks sane, no audit bar needed (they cannot kill).

4 · Refactoring options that need decisions

#DecisionOptions and recommendation
D1RESOLVED Engine provenance is dropped at Stage 3. handoff writes route_rule, matched_rules, pending_reason, release_id; EXTRACTED_COLS excludes them, so run_extract drops all four and csv_to_db imports release_id = NULL — the Stage-2→validation lineage the engine exists to provide is severed. (a) add ENGINE_EXPORT_COLS to EXTRACTED_COLS so they pass through (schema change, ripples to the validation repo's migration — fold into flora-validation#3); (b) record release only in run metadata. Decided: link, don't duplicate — “as long as they can be linked, no need to carry duplicated data”. Shipped: no schema widening; release_id is a --release-id argument to csv_to_db (it names the whole handoff, one per filtered.csv.manifest.json, so it was never a row property); everything else joins on work_id, already in record_metadata and keyed (release_id, work_id) in routing.
D2RESOLVED Curated-source bypass absent from the engine's cheap tier. prescreen_bypass() protects CURATED_SOURCES rows, but the engine's Work has no source field, so the cheap tier could discard rows Stage 3's pre-screen would protect. Latent today (the survivor pool is snapshot-only), real the day curated rows enter the pool. Either add source to the pool schema + Work now, or record the constraint (“curated rows must not enter the pool until this lands”) in CONVENTIONS.md. Decided: add it (“add indeed - and ensure this is correctly documented”). Shipped: Work.source populated and passed to prescreen_bypass(). Note it is currently inert — the pool carries no source column, so nothing is lost today (every pool row is openalex_snapshot); it bites once curated rows can enter the pool (#150).
D3designPhrase policy still lives in two places. Only the seven exclusion patterns are single-sourced from the bundle; the inclusion phrases and guards are duplicated between filter/phrase_detection.py constants and the phrase specs, synced by hand, with a 7-case synthetic “parity” test overstating its coverage. (a) extend the spec-loader approach to inclusion phrases/guards (one edit moves both, as the exclusions already work); (b) generate the Python constants from the specs at import; (c) accept duplication with a real parity test over a large corpus sample. Recommend (a), matching the established pattern.
D4designconventions.json is half-decorative. export.py reads piles and filter_method_prefix; precedence_bands and measurement_levels are read by nothing (bands enforced by convention, levels hardcoded in spec.py). (a) make validate_spec() enforce bands and read levels from the JSON — the policy file becomes real; (b) slim the JSON to the two consumed keys and let CONVENTIONS.md carry the rest as prose. Recommend (a) — a spec outside its band should be a load error.
D5RESOLVED Evidence gate is shape-only. Any non-heuristic measured entry authorizes an autonomous discard — no n, date, owner, sample id, or artifact path required. Decided: leave it — “that's ok”. No tightening of validate_spec(). The bar moved into the promotion recipe instead, where a human reads it, rather than into a schema check that can be satisfied mechanically.
D6RESOLVED search/external_lists.py — implemented I4R / Replication-Network scrapers, never wired into run_search (#46). Decided: off main into a WIP PR. Shipped: deleted from main; preserved on the pushed branch wip/external-lists-curated-harvest, to be finalised against #150.
D7RESOLVED search/engine/cli.py — standalone ingestion path writing candidates_engine.csv, bypassing merge/dedup/ index; only caller is the example script. Decided: delete — “definitely don't maintain duplicates”. Shipped. examples/discover_example.* still invoke it and need a follow-up edit.
D8docsThree competing doc indexes (README.md, docs/README.md, CLAUDE.md §Further Reference). Make docs/README.md the only index; the other two keep one pointer line. Cheap, do with the next docs commit.
D9RESOLVED Two rule evaluators over two corpora. Stage 1's keyword_verdict() (Python constants + pyre_regex) gates data/candidates.csv; the engine (spec bundle, RE2) routes the ~5M-row survivor pool. Nothing downstream reads candidates.csv. CLAUDE.md's “one keyword decision, shared by Stage 1 and Stage 2” is false — Stage 2 never calls it. Stage 1 keeps the Stage A search query (token/stem + concept — the only affordable predicate at 510M rows); every precision decision moves to the engine, with the keyword verdict recorded on the pool row rather than deciding admission. Retire candidates.csv as an admission-gated corpus. Terminal cheap rules stay terminal — that is what the 900s band already is — but as bundle rules, not a second Python copy (_NON_ARTICLE_TYPES etc. in shared/utils.py). Collapsing to one evaluator also deletes the pyre_regex/RE2 divergence class, which is what currently blocks biological-of and data-availability from promotion. Recommend adopting.
