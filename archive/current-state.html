FLoRA Extractor — current state and way forward

The pipeline as it stands after the 2026-08-06 cleanup round, and the plan from here. Supersedes the 2026-08-06 morning page. This page deliberately carries almost no operational numbers: anything derived from the current rule book or run state — pile sizes, handoff rows, cost estimates, set-aside tallies, test counts — goes stale with the next spec promotion or run, so the page names the command or artifact that answers it live instead. A number appears here only when it is external (a price ratio), bound to a named artifact (a snapshot), or a dated measurement of a method (a precision figure with its evaluation report).

The pipeline still cannot run end-to-end. Two blocks, both known, both consequences of the screen moving into Stage 2:

  1. Every stored release is stale. Adding the six screen_* columns moved schema_version, one of the release id's inputs, so export, screen and handoff all refuse — the binding working as designed. The cleanup round moved bundle_hash again (a spec description rewrite), which costs nothing extra: one fresh route over the pool re-mints everything, and existing screen verdicts survive it (they are read across releases within a screening generation).
  2. data/filtered.csv on disk predates the screen columns, so python -m extract.run_extract refuses to start against it — deliberately, rather than silently re-screening. The re-route plus a new handoff fixes this too.

Additionally, migration 0004_claim_expiry.sql must be run in Supabase before the next screen --run; until then every claim fails loudly, naming the file.

1 · What the pipeline is

Stage 1  search/           OpenAlex bulk-parquet snapshot scan (token-stem OR concept gate)
                           → the survivor pool (flat zstd parquet; 5,146,160 rows from the
                             2026-08-03 scan of the 725 GB snapshot); HF share via pool_sync

Stage 2  filter/engine/    JSON rule specs precedence-routed into piles over the pool
                           (discard / screen_expensive / screen_cheap / needs_human / pending)
                           state: Supabase (claims + permanent verdicts, authoritative)
                                  + local DuckDB (derived, disposable) + release JSONs + HF blobs
                           screen_expensive tier = THE screen (2 voters, G-softqual gate)
                           screen_cheap tier     = dormant by design (all its specs shadow)
                           → handoff writes data/filtered.csv atomically, with a manifest

Stage 3  extract/          reads the screen verdict off the row (never re-screens)
                           → resolution ladder (cheapest first, LLM rungs enumerate targets)
                           → outcome coding (two vocabularies) → DOI verification
                           → data/extracted.csv;  sanity_check quarantines on every exit

Stage 4  validate/         read-only Flask dashboard over the CSVs, a parquet mirror and
                           Supabase; the validation import runs from the flora-validation repo

The load-bearing design ideas are real in the code rather than aspirational: rules route and discard, only LLMs admit; content-complete cache keys (prompt version, model-with-effort, inputs) so a differing checkout misses rather than mis-reads; one model constant per question with provider dispatch on the id and no fallback; a transient failure never checkpointed as a definitive answer; Postgres claims as the only cross-machine mutual exclusion, now 6-hour leases; evidence written before the verdict that names it; and a first-success ladder ordered by cost, with deterministic picks withheld until something that can enumerate targets has spoken.

2 · Stage 2, since it is where the plan happens

The rule book is JSON specs in filter/spec/ plus two policy files (conventions.json, folded into the bundle hash; aliases.json, hashed as its own release input). Specs sort by (−precedence, id); the first non-shadow match wins; shadow specs are evaluated and recorded but can never claim a row. python -m filter.engine specs lists what is live right now — the split between live and shadow moves with every promotion, which is why no count is printed here. Two engine-level policies sit above any spec: an unclaimed row is pending / no_filter_matched, and a screen-pile win on an empty abstract is downgraded to pending / no_text. A non-shadow discard that reads text must declare abstract_missing: false, and must carry a measurement at an autonomous level — the loader refuses it otherwise.

Every match is decided by one regex engine (pyarrow's RE2, via eval_spec_batch()); Python re exists in the process only to quote evidence after the pile is settled. A release is a sha256 over six inputs (pool fingerprint, overlay hash, bundle hash, engine version, alias release, CSV schema hash); every consumer re-checks the binding and there is no override.

The expensive tier is the screen: two voters (SCREENING_MODEL_1/_2 in shared/config.py), each answering the validated classification schema; the G-softqual gate (evaluated in analysis/screening_eval/report_v33.md: 89% hard-negative discard, zero settled misses at evaluation) decides discard / proceed / no-decision. Verdicts are permanent rows in Postgres, keyed to a screening generation (voter models + prompt version), read across releases within a generation — a re-route never unasks a voter, and changing a voter or the prompt is what re-opens works. Dry run is the default and prices the batch before any spend: python -m filter.engine screen --tier screen_expensive prints the current pile's size and estimated cost for whatever release is current — that is the number to trust, not any figure written down before the rule book moved.

The cheap tier is dormant by design: all of its specs are shadow, so nothing routes to its pile. The apparatus (two small voters that may only discard on two explicit noes, the prescreen_discard set-aside, --rescreen's reopening) stays wired and tested. What waking it requires is in §6.

3 · Stage 3, briefly

Stage 3 reads the screen verdict off its input row and rebuilds the verdict dict in-process — a missing screen_verdict column is a startup refusal, a blank value writes target_pending, and --screen-here is the explicit escape hatch for hand-made CSVs the engine cannot reach. The resolution ladder runs cheapest-first and returns at first resolution: title-pattern → rule-based citation/candidate match → abstract LLM over candidates → reference-list pick → pre-PDF title search → PDF acquisition and full-text LLM. The two purely deterministic rungs (single_candidate_after_requery, the same-author/year tiebreak) are held-only: the pick is parked, the LLM rungs get their chance to enumerate targets, and the pick is restored only where nothing that could enumerate targets contradicted it. llm_title_search stays quarantined — ~50% precision at its 2026-08 evaluation, never outcome-coded, never imported, and the ladder's dominant OpenAlex cost, since a free-text search bills at 10× a filter query (and a content download at 100× — current prices at the OpenAlex pricing page, deliberately not copied here). Outcome coding runs only on a resolved link; reproductions are coded on two independent axes with per-axis full-text escalation. Every written row's doi_o is verified once (CrossRef → OpenAlex), with unverifiable as its own never-cached outcome so a partial outage cannot delete a DOI.

Operational state — how many rows are extracted, pending, set aside — is read off the artifacts (data/*.csv) or the Stage 4 dashboard, not off this page.

4 · What the 2026-08-06 cleanup round did

The round worked through docs/cleanup-worklist.md — now rewritten in place as the completion record, item by item — as six parallel implementation streams, an independent cross-model review of the full diff, and a docs-vs-code sweep. Highlights that change how the code reads:

  • Dead code deleted rather than documented: the never-firing journal-hint citation scoring (zero production firings; its broken analysis script went with it), the flora_df output machinery, the retired pyre_regex loader field (its record moved to rule_ideas.md), unreachable backfill helpers, legacy cache sweeps.
  • One writer where there were two: export and handoff share one atomic CSV writer (export previously published non-atomically); one UNCHECKED sentinel; one Gemini rotate-and-retry loop behind all three Gemini call shapes.
  • Two real bugs fixed: _study_count_stated checked only each pattern's first match, so a year mention shadowed a later spelled-out study count (now finditer); and the TestRunExtract fixtures pointed at the shared system temp directory, so concurrent test runs corrupted each other — the cause of every "flaky test" report in recent memory, fixed with per-run directories and stable since.
  • PDF acquisition: a designed up-front on-disk check (replaying the recorded winning tier, so pdf_source provenance survives), and a per-URL gone-record — HTTP 404/410 only, never timeouts, 429, 5xx or auth refusals — inside the existing 14-day retry window.
  • The worklist's own errors, corrected in the record: the actor argument it called dead is live (supersede.py passes it); the "double verdict read" it flagged does not exist (measured: one fetch per run; the post-run incomplete count must be a fresh read).
  • Deliberately not done: splitting tiers.py (18 test sites monkeypatch it as a module — re-exports would silently break what they patch); unifying the two self-link guards (they differ behaviorally, not just in structure); unifying the two hash styles (the values are persisted).
  • Docs now match the code, including places the worklist did not know about: a spec table naming a rule id with no file, limitations.md describing three specs that do not ship, a dashboard Promote button with no route, and a contradiction between two docs on the snapshot's size (725 GB is correct). Where a doc described better behavior than the code has, the doc kept the description and the gap is listed in §5 instead (the manifest-verification gap below).

5 · Known weaknesses, ranked

Stale releases + pre-screen handoff block the run blocks the pipeline

See the box at the top. The fix is mechanical: run migration 0004, then route, screen --tier screen_expensive --run, handoff.

A transient read failure can erase the spend record. token_usage._read_all() returns {} on any OSError; the next record() read-modify-writes from that empty dict, destroying the multi-day ledger. The one place a transient failure is promoted to a definitive fact about money.

Stage 3's output is rewritten in place. The four in-process row-loss windows are closed, but there is no temp-file-plus-atomic-replace around extracted.csv as a whole: a SIGKILL during the header rewrite can still leave a header-only file. (Stage 2's writers are all atomic as of this round; Stage 3's is the one that is not.)

The handoff manifest is written but never checked. handoff publishes a manifest naming the CSV's row count and content hash before the CSV, but Stage 3 does not verify the hash of the file it then reads — it only warns when the manifest is absent. The guarantee the docs describe is half-real until the read side checks.

Postgres schema gaps. No index under the hottest verdict read; no migration runner or tracking table (engine_claim_batch is copied whole into three migration files and nothing tests the copies agree); expensive-tier verdicts store an empty prompt_hash; several Python-side invariants have no DB constraint.

The dashboard's cached numbers go stale silently. Nothing under filter/ calls the refresh, and a cached key suppresses recompute (#115). The dashboard is the natural home of every operational count this page refuses to carry, which raises its priority.

pool_reader states two contradictory overlay policies — docstring says "fills, never replaces", code and test replace always. The contract itself is undecided; a maintainer must pick before anyone "fixes" either side.

No CI runs the suite, and the stale feature/extract deploy trigger still ships old code on push. The suite is fast and clean; wiring it to CI is cheap insurance.

6 · The way forward

6.1 · First: unblock and re-baseline

  1. Run migration 0004_claim_expiry.sql in Supabase.
  2. route over the pool (mints fresh release ids under the corrected pool-provenance definition), then screen --tier screen_expensive --run (dry-run first for the price; existing verdicts within the generation are free), then handoff. Stage 3 then has a valid 27-column input again.

6.2 · Rules: draft, validate, promote — incrementally

The machinery for careful rule growth exists end-to-end; what has been missing is the habit loop. The loop per rule:

  1. Draft in shadow. A new spec lands with shadow: true — evaluated and recorded on every route, claiming nothing. rule_ideas.md holds the backlog.
  2. Diagnose. python -m filter.engine diagnose --spec <id>: rows moved per pile, overlap and exclusivity against every other rule, a seeded readable sample.
  3. Measure precision on the rule's own matches. Because live rules are narrow — each touches a small slice of the pool — precision can only be measured on a labelled sample drawn from what the rule matches, not from any general-purpose corpus. This is the evaluated pattern (the OSF registration rules were validated exactly this way) and it becomes the spec's measured entry, which the loader requires before a discard may run live.
  4. Check recall against gold. The complement of the rule-specific sample: run the candidate rule over the known replications present in the pool. data/flora.csv is the gold standard and analysis/gold/README.md already specifies the per-release recall monitor — every release, report which gold works the rule book discards, named against the gold file's hash. The monitor is specified but not built; building it is the highest-leverage piece of new code in this plan, because it converts "we hope no rule discards a real replication" into a number recomputed on every route. (The one live incident of exactly this shape — a real replication among the OSF rule's discards, #163 — was found by hand.)
  5. Promote (shadow: false) with the measurement in the spec; the bundle hash moves, the next route mints a new release, and the audit trail explains itself.

The frozen random holdout (#146-2) is judged not worth building — the maintainer's argument, adopted here: rules this specific need rule-specific validation sets; a random sample of affordable size contains too few of any one rule's matches to say anything about its precision. What survives of the idea is the gold recall half above, where narrowness does not hurt (every rule is scanned over the whole positive set). Open decision: the never-used holdout.json plumbing in spec.py/diagnostics.py can be removed, or repurposed as the seam the gold recall monitor reports through — decide when building the monitor.

6.3 · Wake the cheap tier

The cheap tier's promise is spend: two very small models discard obvious noise before the expensive screen buys two better votes per row. It is dormant because its evidence (analysis/prescreen_eval/REPORT.md) predates the current pool distribution. Waking it is:

  1. Promote one screen_cheap spec (a code-reviewed one-line change; there is deliberately no global switch).
  2. Run it in shadow-of-spend first: route sends rows to the pile, the tier votes, but treat its discards as a labelled sample — re-measure the two-noes discard rule on this distribution before letting it drop anything for real. The gold recall monitor (6.2.4) covers its false-negative side automatically.
  3. Two standing caveats, unchanged: its curated-source bypass cannot fire (the pool schema carries no source column — decide whether to add the column or delete the bypass), and its verdicts may only ever discard; proceed settles nothing.

6.4 · Is the LLM-call design efficient? Mostly yes — the wins are pricing, not restructuring

The question raised: should some LLM calls merge or move now that screening lives in Stage 2? Looking at the call structure per row, the staging logic holds up, and the two real inefficiencies are cheaper to fix with pricing mechanisms than with redesign:

  • Do not merge the screen with target identification. The screen's whole economics is that it runs small models over the many to protect big models from all but the few. Folding target identification into the screen call would pay target-enumeration tokens (and the OpenAlex candidate fetches that prompt needs) on every screened row, most of which the gate discards — a strict loss. It would also couple the two prompts' cache generations: today a target-prompt edit re-buys target answers only; merged, it would re-buy the screen too.
  • The real duplication is the full text, sent twice. A row that reaches the bottom of the ladder sends its full document once to the target call and once to the outcome call — the two largest prompts in the pipeline, paid twice. Two remedies, in order of preference: (1) prompt-cache-aware layout: both providers discount a repeated prompt prefix heavily; putting the document first and identically in both prompts makes the second call's document tokens mostly cached — no semantic change, no cache-key coupling, and prompt_version() is untouched because the prompts themselves do not change, only their block order. (2) one combined full-text call (identify targets and code the outcome per target) — bigger saving, but it couples two evaluated prompts, widens invalidation blast radius, and quietly changes the "outcome coding runs only on a resolved link" policy, since the combined call codes outcomes for links nothing has accepted yet. Do (1); revisit (2) only if cache/token_usage.json shows document tokens still dominating after (1).
  • Batch pricing is the biggest untouched saving. The screen tier is the ideal batch-API customer: offline, claimed in advance, thousands of independent single-turn calls, no interactivity. Both OpenAI and Gemini batch modes halve the price. The tier already runs flex where available; moving the claimed batch to the batch APIs roughly halves the screen bill again at the cost of latency the tier does not care about. Outcome coding's abstract pass batches the same way.
  • Moving Stage 3's LLM rungs into the engine's tier machinery (claims, permanent verdicts, HF blobs) would buy shareable resume — two machines dividing a Stage 3 run without re-paying, today impossible because resume is a local artifact (#136 §3). That is an operations win, not a token win, and it is the natural long-term home; but it is a real redesign, and nothing above depends on it. Sequence it after the gold monitor and the cheap tier, if at all.
