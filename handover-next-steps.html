FLoRA Extractor — Handover & Next Steps

State as of 2026-08-04, covering the work since ~2026-07-25. Written for the returning maintainer: conceptual changes and pending decisions up front, PR history for the details.

1. The one-paragraph summary

The pipeline was inverted. Ten days ago it searched APIs by keyword, filtered candidates down with a second keyword pass plus an LLM filter, and extracted from whatever survived. Today it scans the entire OpenAlex snapshot once (510M works → a 5.1M-row survivor pool), routes that pool with a declarative, measured rule engine whose principle is "rules route and discard; only LLMs admit", and runs a redesigned Stage 3 built around a validated two-voter screen, a single merged target prompt, one row per original paper, and separate outcome vocabularies for replications and reproductions. Every prompt and rule now carries an explicit evidence status — measured, structurally justified, or shadow pending measurement. Nothing has been spent on screening the pool yet — the first paid run is waiting on your go-ahead, after a fresh routing (§6, decision 1; the superseded pre-#162 sizing came to ~$152 all-in).

2. The pipeline today

Stage 1: search/        → SEARCHES only              → survivor pool (parquet, ~5.1M rows)
Stage 2: filter/engine/ → routes the pool into piles → data/filtered.csv (handoff)
Stage 3: extract/       → finds original + outcome   → data/extracted.csv
Stage 4: validate/      → read-only dashboard        → (no CSV output)

python -m search.run_search --scan                             # Stage 1 (snapshot scan)
python -m filter.engine route                                  # Stage 2: routing release
python -m filter.engine screen --tier screen_expensive --run   # Stage 2: claimed LLM tier
python -m filter.engine handoff --out data/filtered.csv        # Stage 2 → Stage 3
python -m extract.run_extract                                  # Stage 3
python -m extract.csv_to_db                                    # push to Supabase validation

3. What changed conceptually, stage by stage

Stage 1 — from API keyword search to a snapshot scan (PRs #129/#142, #159)

  • The whole snapshot is scanned, once. The 2026-08-03 production scan processed all 510,372,821 snapshot records on a throwaway EC2 instance and wrote a survivor pool of 5,146,160 rows (2,232 parquet files), verified on HF. Recall questions now separate cleanly into three layers: snapshot coverage (exhaustive), the search gate's vocabulary (deliberately broad, but still a choice), and what OpenAlex itself indexes — grey-literature reproduction reports remain a known blind spot (#150).
  • Stage 1 only searches. Its exclusion patterns and second-pass keyword filtering were deleted (#159), leaving one intentionally broad search gate — a token/stem + concept vocabulary (filter/phrase_detection.py) — and every survivor enters the pool. Anything smarter is Stage 2's job, where it is measured and reversible. The old API discovery sources were retired to wip/api-harvest-sources (#158).

Stage 2 — from rule_filter + LLM filter to the filter engine (#146 → PR #152; #161, #162)

  • The old Stage 2 is deleted (rule_filter.py, run_filter.py, the LLM filter). Its replacement is filter/engine/: JSON specs with precedence bands, deterministic routing releases, and claimed, budget-gated LLM screening tiers — a claim in Postgres is what permits spend, so two collaborators cannot double-screen or double-pay for the same rows.
  • The rule book was inverted to a whitelist (design + all measurements: redesign/rulebook_v2.html). Nothing is screened unless a positive admission rule asks for it; the default pile is pending, not discard. As of #162 the live set is deliberately narrow: the structural discards (non-paper DOIs/titles, non-report/study types, deposits) plus two live admissions — replication-claim-cited-title (the strongest rung of the four-spec claim ladder, → expensive tier) and osf-registration-completed. Everything else runs shadow — counted, never acting — until measured: the other three claim-ladder rungs, reproduction-signal, the broad replication-signal/replication-probe, and the osf-registration-protocol discard (its template vocabulary is not yet fully enumerated). The spec files themselves ("shadow": true) are the authority on this, not any document.
  • Promotion is evidence-gated. A statistical rule goes live on a "rule of three" sample sizing (n ≥ 3V/L for discard volume V and tolerable loss L); structural rules need an argument, not a sample. data/flora.csv (1,553 measurable DOIs) is the gold standard for recall checks. The per-release, per-rule recall monitor is designed (analysis/gold/README.md) but not yet built — today the check is a hand count against flora.csv, and building the monitor is a next step (§7). The old 7.5k "gold corpus" was deleted deliberately: 62% of it was the previous pipeline's own LLM verdicts, so recall against it was circular.
  • The cheap pre-screen moved here. The discard-only two-tiny-voter tier (shared/prescreen.py) is no longer a Stage 3 flag; which rows get it is a routing decision (the screen_cheap pile), and it can only discard on two explicit noes (#161, #135).

Stage 3 — redesigned front door, linking, and outcome coding (PRs #116–#127)

  • The screen is validated and defined once. Two voters (Gemini light + gpt-5.4-mini) answer the v3.3 schema; the gate (screen_gate(), "G-softqual") was chosen on labelled evaluation data (320 positives, 70 hard negatives): ~85–89% hard-negative discard across runs, with 0–1 missed positives — a spread the eval attributes to run-to-run model variance, and measured in-sample (analysis/screening_eval/report_v33.md). The old screen_disagreement terminal state is gone — confident splits proceed. v3.3 folded the six FLoRA FAQ coding rules and the partial-overlap rule into the prompt.
  • One target prompt, one namespace, one row per original. The abstract, reference-list and full-text rungs of the resolution ladder now share a single prompt (build_target_prompt()); candidates and references live in one deduplicated @smith2009 key namespace so a re-fetched list can never renumber a cached pick. The parallel "multi pipeline" is deleted: a per-target adapter writes one row per original paper, collapsing multiple studies of one original into study_o, and study_r now records which study of the replication re-tests each original. A deterministic early rule withholds its pick when the paper's own text can't rule out a second target, so cheap rungs no longer truncate multi-target papers.
  • Reproductions get their own vocabulary. Outcome coding split into two prompts: replications keep the FLoRA outcome ladder; reproductions are coded on two independent axes — computation (reproducible / issues / technical failure / not checked) and robustness (robust / challenges / not checked) — each with its own quote and escape hatch. record_type_check lets the full-text pass re-route a mis-typed row to the other vocabulary once.
  • Weak evidence is contained, not laundered. llm_title_search (~50% precision, and 10× OpenAlex cost) is provisional: bottom of the ladder, never outcome-coded, never imported, set aside for human confirmation. Full-text provenance (pdf_source, parse_method) is on every row, and there is no landing-page-HTML substitute for a document any more.

Cross-cutting discipline

  • Prompts and caches: every prompt lives in shared/prompts.py; prompt_version() hashes the text plus every spliced fragment, and cache keys name everything the answer depends on (prompt version, model, thinking level, inputs) — editing a prompt invalidates exactly its caches. The caching rule: a definitive answer is cached even when negative (a decline, a "no candidates"); an unreadable reply, an incomplete multi-voter screen, or a provider failure is retried and never cached — a 503 must never be checkpointed as a miss.
  • Spend control: per-day/provider/model token accounting, a hard OpenAI daily budget (clean stop, not a crash), OpenAI/Gemini flex tiers, a Gemini thinking-level knob, and an explicit OpenAlex cost model (title search = 10× a filter query; content download = 100×) that shaped the ladder's ordering.
  • Settings split (#161): a constant (model ids, thresholds, vocabularies — anything that decides what the pipeline concludes) is a plain Python value changed by commit; a tunable (rate limits, paths, timeouts) is env-read in shared/config.py. If an override could make two collaborators grade the same row differently, it is a constant.
  • Tests: trimmed to contracts (#119, with further trims alongside the engine work): one test per seam, a no-network guard, suite runtime cut from minutes to seconds. Exact counts move; the principle — delete a test when its code path dies — is the durable part.

5. The number to keep in view: 4.4M pending

85.7% of the pool matched no rule at all (pending/no_filter_matched). Under the whitelist that is by design — but an unsampled pending pile is a silent discard pile. The standing obligation from the rule-book proposal: sample the pending pile every release. Two distinct checks, neither yet operational: (a) gold overlap — count which flora.csv papers sit in pending (cheap once the recall monitor is built, but it can only see papers we already know about); (b) a stratified read of a random pending sample — the rule book calls for stratifying by work type and oversampling software/component/database/supplementary-materials — which is the only way to find relevant papers absent from the gold set. If pending sampling lapses, the whitelist's honesty claim lapses with it.
