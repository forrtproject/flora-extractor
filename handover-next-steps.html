FLoRA Extractor — Handover & Next Steps

Updated 2026-08-05 after the first end-to-end run and the reviewer comments on the 2026-08-04 draft. Covers the work since ~2026-07-25: conceptual changes, the data architecture, and what comes next — PR history holds the details.

1. The one-paragraph summary

The pipeline was inverted, and it has now run end to end. Ten days ago it searched APIs by keyword, filtered candidates down with a second keyword pass plus an LLM filter, and extracted from whatever survived. Today it scans the entire OpenAlex snapshot once (510M works → a 5.1M-row survivor pool), routes that pool with a declarative, measured rule engine whose principle is "rules route and discard; only LLMs admit", and runs a redesigned Stage 3 built around a validated two-voter screen, a single merged target prompt, one row per original paper, and separate outcome vocabularies for replications and reproductions. Every rule now carries an explicit evidence status — measured, structurally justified, or shadow pending measurement — which will allow us to shrink the pending pile incrementally. On 2026-08-04/05 the whole loop ran for real: route → screen (every admitted work now carries a verdict) → handoff → Stage 3 over 1,837 works, ≈$5.30 actual LLM spend. The loop works; the job from here is growing the rule book tranche by tranche (§6).

2. The pipeline today

Stage 1: search/        → SEARCHES only              → survivor pool (parquet, ~5.1M rows)
Stage 2: filter/engine/ → routes the pool into piles → data/filtered.csv (handoff)
Stage 3: extract/       → finds original + outcome   → data/extracted.csv
Stage 4: validate/      → read-only dashboard        → (no CSV output)

python -m search.run_search --scan                             # Stage 1 (snapshot scan)
python -m filter.engine route                                  # Stage 2: routing release
python -m filter.engine screen --tier screen_expensive --run   # Stage 2: claimed LLM tier
python -m filter.engine handoff --out data/filtered.csv        # Stage 2 → Stage 3 (screened-only by default)
python -m extract.run_extract                                  # Stage 3 (resumes by default; --fresh restarts)
python -m extract.csv_to_db                                    # push to Supabase validation

All commands assume the repo's virtualenv is active (source .venv/bin/activate, or call .venv/bin/python directly) — macOS ships no bare python, so a fresh shell without the venv will report "command not found". Setup: docs/setup.md.

Known gap — a pulled pool is not verified. pool_sync --pull skips files whose byte size already matches and compares nothing else: the manifest's row counts are recorded on push but never checked on pull, there is no checksum step, and a pulled pool has no scan ledger — which also silently degrades the release id's pool-provenance input to a constant. Until a --verify exists, the practical check after a pull is: file count and total rows against the HF pool_manifest.json (ledger_files / ledger_kept), and the gate fingerprint match that --pull already warns about.

4. What changed conceptually, stage by stage

Stage 1 — from API keyword search to a snapshot scan (PRs #129/#142, #159)

  • The whole snapshot is scanned, once. The 2026-08-03 production scan processed all 510,372,821 snapshot records on a throwaway EC2 instance and wrote a survivor pool of 5,146,160 rows, verified on HF. Recall questions now separate into three layers: snapshot coverage (exhaustive), the search gate's vocabulary (deliberately broad, but still a choice), and what OpenAlex itself indexes — grey-literature reproduction reports remain a known blind spot (#150).
  • Stage 1 only searches. Its exclusion patterns and second-pass keyword filtering were deleted (#159), leaving one intentionally broad search gate (filter/phrase_detection.py), and every survivor enters the pool. Anything smarter is Stage 2's job, where it is measured and reversible. The old API discovery sources were retired to wip/api-harvest-sources; the non-OpenAlex sources need to be brought back in (#158).

Stage 2 — from rule_filter + LLM filter to the filter engine (#146 → #152; #161, #162, #165)

  • The old Stage 2 is deleted (rule_filter.py, run_filter.py, the LLM filter). Its replacement is filter/engine/: JSON specs with precedence bands, deterministic routing releases, and claimed, budget-gated LLM screening tiers backed by the live Postgres claim tables.
  • The rule book is a whitelist. Nothing is screened unless a positive admission rule asks for it; nothing is discarded unless a specific rule rules it out. The default pile is pending, not discard. Currently live: the structural discards (non-paper DOIs/titles, non-report/study types, deposits, and — promoted 2026-08-05 after the maintainer re-adjudicated the one blocking case as a mock write-up — osf-registration-protocol) and three admissions to the expensive tier: replication-claim-cited-title, replication-claim-title-strong, osf-registration-completed. In shadow (counted, never acting): the weaker claim-ladder rungs (-text, -residual, -title-broad), reproduction-signal, replication-signal, replication-probe. The spec files ("shadow" in filter/spec/*.json) are the authority; this list is a snapshot.
  • Promotion is evidence-gated. Additional rules should only be added based on evidence — especially when they discard entries. This can be logical (e.g. ineligible article_type) or empirical (manual or LLM-supported screening of a sufficient sample). data/flora.csv (1,553 measurable DOIs) is the gold standard for recall checks, though it is not sufficient yet, given that reproductions are missing — that is a reason for getting the TRN reproductions in asap. The per-release recall monitor is specified in analysis/gold/README.md — join the flora keys against a routing release, no LLM and no sampling, and report per rule how many known-good papers it discarded plus how many no rule reached — but not yet implemented; today that check is a hand count.
  • A cheap pre-screen can be used for low-precision rules. The discard-only two-tiny-voter tier (shared/prescreen.py) can only discard on two explicit noes (#161, #135). At the moment, we should focus on high-precision rules that make "expensive" screening worthwhile, but will likely have to return to this for larger batches; it needs to be validated on a more diverse pool once we add imprecise rules (estimated true-positive rate below ~75%).

Stage 3 — redesigned front door, linking, and outcome coding (PRs #116–#127, #166)

  • The screen is validated and defined once. Two voters (Gemini light + gpt-5.4-mini) each answer the revised prompt, which includes the coding rules from the FLoRA FAQ; the gate (screen_gate()) was chosen on labelled evaluation data (analysis/screening_eval/report_v33.md). Confident splits proceed; the old screen_disagreement terminal state is gone.
  • One target prompt, one namespace, one row per original. The abstract, reference-list and full-text rungs of the resolution ladder share a single prompt; candidates and references live in one deduplicated @smith2009 key namespace so a re-fetched list can never renumber a cached pick. The parallel "multi pipeline" is deleted: a per-target adapter writes one row per original paper, and study_r records which study of the replication re-tests each original.
  • Reproductions get their own vocabulary. Replications keep the previous outcome values (with minor clarifications); reproductions are coded on two independent axes — computation and robustness — each with its own quote and escape hatch.
  • Weak evidence is contained. llm_title_search (~50% precision, 10× OpenAlex cost) is provisional: never outcome-coded, never imported, set aside for human confirmation; an additional LLM pass to validate the candidates might be worth implementing. Full-text provenance (pdf_source, parse_method) is on every row.
  • Run operations (new in #166): Stage 3 processes rows concurrently (EXTRACT_WORKERS, default 4, ~4× wall-clock), resumes by default (--fresh restarts loudly), and skips both papers already in FLoRA and the 1,770 legacy already-validated records (data/validated_skip.csv) before spending anything.

Cross-cutting discipline

  • Prompts and caches: every prompt lives in shared/prompts.py; prompt_version() hashes the text plus every spliced fragment, and cache keys name everything the answer depends on. The caching rule: a definitive answer is cached even when negative; an unreadable reply, an incomplete multi-voter screen, or a provider failure is retried and never cached. Open design question: this granularity means any prompt edit, however cosmetic, discards all verdicts made under it — we need a way to keep verdicts across minor wording changes, e.g. warn on a changed prompt and ask whether to invalidate or retain (§6).
  • Spend control: per-day/provider/model token accounting; a hard OpenAI daily budget that matches our free tokens there (clean stop, not a crash); OpenAI/Gemini flex tiers and a Gemini thinking-level knob; and an explicit OpenAlex cost model (title search = 10× a filter query, content download = 100×) that shaped the ladder's ordering.
  • Settings split (#161): a constant (anything that decides what the pipeline concludes) is a plain Python value changed by commit; a tunable (rate limits, paths, timeouts) is env-read in shared/config.py. If an override could make two collaborators grade the same row differently, it is a constant.
  • Tests: trimmed to contracts: one test per seam, a no-network guard, suite runtime cut from minutes to seconds; a test is deleted when its code path dies.

5. The first end-to-end run (2026-08-04/05)

The loop ran for real, authorized at ≤$15: route under the committed bundle → claimed two-voter screen → screened-only handoff (1,837 works after 33 tier discards) → Stage 3 over the whole corpus. Actual LLM spend for the Stage 3 pass was ≈$5.30 with flex (≈$10.59 at list price). Counts read off the files:

Two operational lessons. First, the ~1,000 new target_pending rows are deposit-type records (OSF, Zenodo, SAGE) that carry no reference metadata in OpenAlex, so the ladder has nothing to resolve against — whether to loosen the title-search gate for them is an open policy question (§6). Second, on pricing: the engine's dry-run quotes are list-price upper bounds — they model prompt length but not flex discounts or OpenAI prompt caching — and the measured run came in at roughly half list. Plan future tranches from measured per-row cost (well under 1¢/row for screening, ~$0.003/row for this Stage 3 corpus), not from dry-run totals.

Current routing state (release 6aad75c0c5a0, 2026-08-05): discard 557,606 · pending 4,583,904 · screen_expensive 4,650 — and every admitted work already carries a verdict, because verdicts follow the work across releases: re-routing never re-buys a screen.

6. The path through the backlog

4.58M pool rows are pending — matched by no rule. That is the whitelist working as designed: pending is not a verdict, it is the backlog. The path through it is incremental and now proven end to end:

  1. Author the next admission rule (the candidate list, with regexes and every rejected idea, is filter/spec/rule_ideas.md), ship it in shadow, and size it against the pool for free.
  2. Validate it — logically for structural rules, empirically for statistical ones (manual or LLM-supported reading of a sufficient sample of what it matches and what it would discard), using flora.csv and other benchmark sources (e.g. TRN) for recall.
  3. Promote, route, screen, extract — the §5 loop, per tranche, with measured costs.
  4. Keep the honesty checks running: known-good papers in pending (the gold monitor, once built) and stratified reads of random pending samples — the only way to find relevant papers absent from the gold set. The rule book calls for stratifying by work type and oversampling software/component/database/supplementary-materials.

A note on the shadow sizing that set this order: replication-signal alone matches ~1.09M rows (21% of the pool). The broad rules are held shadow not because screening them is expensive in dollars but because a discard-only cheap tier over a million rows is a recall risk that has to be measured first. Pending also contains a small distinct slice — pending/no_text: a rule matched but there is no abstract to screen — whose remedy is text backfill, not new rules.

7. Decisions and open questions

  1. Title-search policy for deposit-type records. ~1,000 target_pending rows from the first run are deposits with no reference metadata; the only automated path to their originals is the provisional title search (~50% precision, 10× OpenAlex cost). Loosen the gate for this class, add an LLM validation pass over its candidates, or route them to human review?
  2. Push the run's results to validation? csv_to_db has not been run on the new resolved rows — deliberately left as your call.
  3. RPP registrations scope. The OSF Open-Ended keep arm admits 336 rows that are almost entirely Reproducibility Project: Psychology registrations; for an individual RPP study that registration may be the only record that exists. FLoRA scope call, recorded not answered.
  4. Verdict retention across minor prompt edits. Today any prompt change invalidates all its cached verdicts by design. We need a mechanism to keep verdicts on minor changes — plausibly: warn on a version change and ask whether to invalidate or retain.
  5. Claims lifecycle defaults. Now exercised live, but two implementer defaults still await your review: there is no lease/TTL, so a dead run leaves an active claim a human must mark failed; and the measurement tier neither takes nor respects the per-work lock.
  6. Git workflow: decide whether to use dev plus branch-protected main — would seem worth it, but currently dev is very stale.
  7. Issue #144 (staged waves) needs a review pass: it remains the framing document for scaling through the corpus, but it was written before the engine loop existed and its pilot questions are partially overtaken by the first live run.

8. Next steps (roughly in order)

  1. Run the loop — this is the key thing now. Rules → route → screen → handoff → extract, tranche by tranche through the pending backlog (§6). Everything through PR #167 is merged; the tree is clean.
  2. Build the two honesty checks: the gold recall monitor (analysis/gold/README.md is the spec; implementation belongs in filter.engine diagnose) and a repeatable stratified pending-pile audit.
  3. Get the TRN reproductions in — both as benchmark coverage for reproduction recall and as the evidence base for the reproduction routing rule (#155).
  4. Bring the non-OpenAlex discovery sources back (#158), and the curated harvester for OSF/I4R/HAL/EconStor reproduction reports (#150 — likely not all are needed).
  5. Close the pool-verification gap (§3): a pool_sync --verify that checks pulled files and row counts against the manifest.
  6. Construct the holdout when discard pressure grows. filter/spec/holdout.json does not exist yet; the Postgres registry for it does. It is a frozen, labelled evaluation set for measuring rules without re-using their derivation data. Admission rules don't need it — a false admission just costs a screen — so it binds when we start promoting broader discard rules; construction (size, gold/random mix, refresh policy) is #146 open decision 2.
