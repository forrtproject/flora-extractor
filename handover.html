FLoRA Extractor — pipeline status & handover

Written 2026-08-10, at commit d6d2f4e on main. Every number on this page was read off a file or a read-only command, not inferred from the code. Section 1 explains how the pipeline works. Section 2 says where it stands today. Section 3 is the runbook. Sections 4 and 5 cover open work and where the rest of the documentation lives.

1. How the pipeline works

FLoRA Extractor finds replication and reproduction studies for the FLoRA database. For each candidate paper, it identifies which original study the paper re-tested and what the outcome was. The work happens in four stages. Each stage narrows the set of papers further.

Stage 1  search/         scans the OpenAlex snapshot        → the survivor pool (~5.1 million papers)
Stage 2  filter/engine/  routes and screens the pool         → a few thousand admitted papers
Stage 3  extract/        links each paper to its original    → verdicts, rendered as data/extracted.csv
Stage 4  validate/       read-only dashboard                 → monitoring only, writes nothing

The four stages in plain terms

  • Stage 1 — search. A one-off scan of the full OpenAlex snapshot (725 GB) keeps every paper that passes a keyword gate. The result is the survivor pool: about 5.1 million rows of parquet, shared through a private Hugging Face repository. You almost never re-run this stage. You pull the pool instead.
  • Stage 2 — filter. A rule book of JSON specs sorts the pool into piles. Rules can only route or discard. Only an LLM screen can admit a paper. The screen asks two models to vote on each paper; a paper proceeds unless the votes say it is not a replication. Screening runs as a claimed job: each machine claims a batch first, so two machines never pay for the same paper.
  • Stage 3 — extract. For each admitted paper, a ladder of steps tries to find the original study, cheapest step first: title patterns, then citation matches, then LLM calls over the abstract, the reference list, a title search, and finally the full text. The same reading also codes the outcome (success, failure, mixed, and so on). Each paper ends in one permanent verdict stored in Postgres. A separate export command turns the stored verdicts into data/extracted.csv.
  • Stage 4 — monitor. A local Flask dashboard that reads the CSVs and the validation tables. It is pipeline diagnostics, not the validation step itself, and it changes nothing.

Validation proper happens in a separate application. This repository stops at data/extracted.csv. The separate flora-validation repository pushes those rows into the Supabase validation tables and provides the app in which humans review them. The final product is the Supabase validated table.

Terms this page uses

TermMeaning
workOne paper as it moves through the pipeline. Identified by its OpenAlex work id.
releaseOne run of the Stage 2 rule book over the pool. Each release has an id and fixes which works sit in which pile. The store keeps every release, so commands that depend on one must name it with --release.
verdictThe permanent result row Stage 3 stores for a work. Verdicts live in Postgres and outlive the routing that produced them. The verdict, not a file, is the checkpoint: a re-run skips every work whose verdict settles it.
generationA version stamp for Stage 3's logic: a hash over its prompts, models and ladder version. Each verdict records the generation it was made under. When you edit a prompt or a model, the stamp changes, and works whose verdicts carry the old stamp count as unfinished again — the next run re-decides them with the new logic. Until new verdicts exist, the export renders the old ones, so the CSV never goes empty in between.
claimA short lease on a batch of works. Both LLM stages claim before they spend, which is what lets several machines share the screening and extraction work safely.
set-asideA row the export files into a separate CSV instead of extracted.csv, because it is not ready for validation (for example, no original found yet).
skip listsTwo lists of papers already in FLoRA or already in the validation tables. Both the worklist and the export honour them, always, with no flag.
sandbox--mode validation: a full test run of Stage 3. It stores its verdicts under a separate label, so the live export does not pick them up. Because every LLM answer is cached, repeating the same works live re-uses those answers — so promoting a good sandbox run costs almost nothing. The first run of changed code always goes here.

Three design rules worth knowing before you touch anything

  • Every API call is cached, and the cache key names everything the answer depends on (prompt version, model, reasoning effort, inputs). Re-runs are near-free. The caches are shared through Hugging Face, so a collaborator pulls them instead of paying the provider again.
  • One model per call site, no fallback. Every model is a named constant in shared/config.py. When a provider fails, the row records the failure; no other model answers in its place.
  • A transient failure is never a result. api_error in a field means "failed after retries"; it is never checkpointed as a definitive answer, and the next run asks again.

3. Runbook — how to put entries through the pipeline

3.0 One-time setup

Copy .env.example to .env and set these variables:

  • RESEARCHER_EMAIL — for the OpenAlex and CrossRef politeness headers.
  • GEMINI_API_KEY and OPENAI_API_KEY — the screen and extraction models.
  • OPENROUTER_API_KEY — only if you use models through OpenRouter. An OpenRouter model id contains a "/" (for example qwen/qwen3-30b); check the model constants in shared/config.py to see whether any current model does.
  • SUPABASE_SERVICE_KEY — required by every claimed --run. The claim is what stops two machines paying for the same works. SUPABASE_URL ships in .env.defaults.
  • HF_TOKEN — the pool and cache repositories on Hugging Face are private. Alternatively, run hf auth login once.

Use the project venv (.venv). Then pull the shared artefacts instead of recomputing them:

python -m shared.cache_sync --pull     # the shared API and LLM caches
python -m search.pool_sync --pull      # the ~7 GB survivor pool and its provenance sidecar

3.1 Stage 1 — only when the corpus itself must change

python -m search.run_search --scan

This scans the full 725 GB OpenAlex snapshot and takes many hours. Run it on an EC2 instance in the snapshot's own region, so the data transfer stays local; the runbook is docs/aws-snapshot-scan.md. The --scan flag is required precisely so nobody starts the scan by accident. Normally you pull the pool instead (section 3.0).

3.2 Stage 2 — route, screen, hand off

python -m filter.engine route          # runs the rule book → a NEW release; note its id
python -m filter.engine status         # lists all releases and their pile counts

The store holds many releases, so every release-bound command refuses to run without --release. Use --release latest for the newest release, or name one — a unique prefix is enough (--release fc10). The current release is fc10feb6b50c.

python -m filter.engine screen --tier screen_expensive --release <id>        # dry run: cost estimate
python -m filter.engine screen --tier screen_expensive --release <id> --run  # the real screen
python -m filter.engine handoff --out data/filtered.csv --release <id>       # the record artefact

Without --run, screen is a dry run: it prints the row count and a cost estimate, and spends nothing. The handoff writes a manifest sidecar (data/filtered.csv.manifest.json) naming the release and row count.

3.3 Stage 3 — extract, then export

The tier and the export also refuse without --release. One rule before anything else: the first run of changed code goes through the sandbox. Sandbox verdicts are real but invisible to the live export, and promoting them is just re-running live — near-free, because every LLM call is cached.

# Sandbox first, if any Stage 3 code, prompt or model changed:
python -m extract.tier --run --mode validation --release <id>
python -m extract.export --release <id> --mode validation --out data/extracted-test.csv
# Read the sandbox rows before going live.

python -m extract.tier --release <id>             # dry run: worklist size and cost estimate
python -m extract.tier --run --release <id>       # the real run: claim → ladder → one verdict per work
python -m extract.export --release <id>           # verdicts → data/extracted.csv (whole file, atomic)
python -m extract.export --release <id> --check   # read-only: diff the store against the file
python -m extract.sanity_check                    # integrity report over the exported CSV
python -m extract.audit_dois                      # re-verify original DOIs; --apply supersedes verdicts

The last two overlap less than they look. sanity_check is a read-only report over the whole CSV: schema, cross-field contradictions, and (with --deep) two network checks. audit_dois does one job: it re-checks every doi_o against the DOI registries and, under --apply, writes corrected verdicts. Run sanity_check after every export; run audit_dois when you have reason to doubt the DOIs.

What a re-run does, and does not, redo:

  • The worklist is rebuilt between batches. It subtracts settled works, works on the skip lists, works resting on a fresh target_pending (14 days), and anything the named release does not admit. api_error retries at once. Note that a plain re-run of a rested target_pending work is likely fruitless: nothing about the evidence has changed. What to do with these works long-term is an open question (section 4).
  • --redo W1,W2 re-extracts named works and supersedes their old verdicts.
  • Editing a prompt or a model mints a new generation, which reopens every work at once. Do this knowingly. Two things soften the cost. First, the LLM cache: if an edit provably does not change the answer, you can declare the old and new cache keys equivalent (issue #171's mechanism: register the legacy key parts in a module-level constant and read through read_cache_migrating() in shared/cache.py), and the existing answers keep serving. Second, even without a declared equivalence, only the calls the edit actually touches miss the cache; everything else on a reopened work replays free.

3.4 Stage 4 — watch

python -m validate.app          # dashboard at http://localhost:5001

3.5 Hand over to validation

Give data/extracted.csv to the flora-validation repository. Its csv_to_db.py inserts the rows into the three Supabase validation tables in one idempotent transaction (ON CONFLICT (pair_id) DO NOTHING). Only rows with a settled outcome and a paper type are ready — 1,406 of the current 1,899.

3.6 What a run costs

  • OpenAI: the daily 9.5M-token budget described in section 2. When it is exhausted, the run stops cleanly and the rows written so far stay.
  • OpenAlex bills credits per request, and not uniformly: id and DOI lookups are free, list queries cost 1×, free-text searches 10×, content downloads 100×. Title searches are why the search steps sit at the bottom of the Stage 3 ladder. On a full campaign day, the OpenAlex budget, not tokens, is the binding constraint.
  • Estimate before you spend. Both stages print a dry-run estimate; read it first. While we confirm the budget, only Lukas should spend Gemini and OpenRouter tokens (they cost real money) beyond very small test runs.
