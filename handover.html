1. How the pipeline works

FLoRA Extractor finds replication and reproduction studies for the FLoRA database. For each candidate paper, it identifies which original study the paper re-tested and what the outcome was. The work happens in four stages. Each stage narrows the set of papers further.

Stage 1  search/         scans the OpenAlex snapshot        → the survivor pool (~5.1 million papers)
Stage 2  filter/engine/  routes and screens the pool         → a few thousand admitted papers
Stage 3  extract/        links each paper to its original    → verdicts, rendered as data/extracted.csv
Stage 4  validate/       read-only dashboard                 → monitoring only, writes nothing

The four stages in plain terms

  • Stage 1 — search. A one-off scan of the full OpenAlex snapshot (725 GB) keeps every paper that passes a keyword gate. The result is the survivor pool: about 5.1 million rows of parquet, shared through a private Hugging Face repository. You almost never re-run this stage. You pull the pool instead.
  • Stage 2 — filter. A rule book of JSON specs sorts the pool into piles. Rules can only route or discard. Only an LLM screen can admit a paper. The screen asks two models to vote on each paper; a paper proceeds unless the votes say it is not a replication. Screening runs as a claimed job: each machine claims a batch first, so two machines never pay for the same paper.
  • Stage 3 — extract. For each admitted paper, a ladder of steps tries to find the original study, cheapest step first: title patterns, then citation matches, then LLM calls over the abstract, the reference list, a title search, and finally the full text. The same reading also codes the outcome (success, failure, mixed, and so on). Each paper ends in one permanent verdict stored in Postgres. A separate export command turns the stored verdicts into data/extracted.csv.
  • Stage 4 — monitor. A local Flask dashboard that reads the routing store, the exported CSVs and the validation tables. It is pipeline diagnostics, not the validation step itself, and it changes nothing.

Validation proper happens in a separate application. This repository stops at data/extracted.csv. The separate flora-validation repository pushes those rows into the Supabase validation tables and provides the app in which humans review them. The final product is the Supabase validated table.

Terms this page uses

TermMeaning
workOne paper as it moves through the pipeline. Identified by its OpenAlex work id.
releaseOne run of the Stage 2 rule book over the pool. Each release has an id and fixes which works sit in which pile. The store keeps every release, so commands that depend on one must name it with --release (can be --release latest).
verdictThe permanent result row Stage 3 stores for a work. Verdicts live in Postgres and outlive the routing that produced them. The verdict is also the resume state: a re-run skips every work whose stored verdict settles it, so a crashed or budget-stopped run simply continues — no output file is consulted.
ladderStage 3's ordered list of resolution steps, cheapest first (title patterns → citation matches → LLM calls over abstract, references, search, full text). EXTRACT_LADDER_VERSION in extract/link_original.py numbers its revisions; each verdict records the ladder it was written under, as provenance only.
generationA version stamp for Stage 3's logic: a hash over its prompts and models. Each verdict records the generation it was made under. When you edit a prompt or a model, the stamp changes, and works whose verdicts carry the old stamp count as unfinished again — the next run re-decides them with the new logic. Until new verdicts exist, the export renders the old ones, so the CSV never goes empty in between. The ladder version is deliberately NOT in the hash: a ladder change usually adds sources or rungs, so already-matched works do not need revisiting. When a change should reach settled works, they are reopened by name (--redo-status).
claimA short lease on a batch of works. Both LLM stages claim before they spend, which is what lets several machines share the screening and extraction work safely.
set-asideA row the export files into a separate CSV instead of extracted.csv, because it is not ready for validation (for example, no original found yet).
skip listsTwo lists of papers already in FLoRA or already in the validation tables. Both the worklist and the export honour them, always, with no flag.
sandbox--mode validation, on the Stage 3 tier and export and on the Stage 2 screen alike: a full test run whose verdicts are stored under a separate label, so the live export, the handoff and the live checkpoint do not pick them up. Because every LLM answer is cached, repeating the same works live re-uses those answers — so promoting a good sandbox run is just re-running live, at almost no cost. The first run of changed code should always go here (a convention, not enforced by the tools).

Three design rules worth knowing before you touch anything

  • Every API call is cached, and the cache key names everything the answer depends on (prompt version, model, reasoning effort, inputs). Re-runs are near-free. The caches are shared through Hugging Face, so a collaborator pulls them instead of paying the provider again. After substantial screening or extraction work, publish your answers with python -m shared.cache_sync --push — both tiers print this reminder at the end of any run that spent. The engine's own screen and extract response caches are pushed by the tiers themselves at the end of a run; the manual push covers the general API caches.
  • One model per call site, no fallback. Every model is a named constant in shared/config.py. When a provider fails, the row records the failure; no other model answers in its place.
  • A transient failure is never a result. api_error in a field means "failed after retries"; it is never checkpointed as a definitive answer, and the next run asks again.

3. Runbook — how to put entries through the pipeline

3.0 One-time setup

Copy .env.example to .env and set these variables:

  • RESEARCHER_EMAIL — for the OpenAlex and CrossRef politeness headers.
  • GEMINI_API_KEY and OPENAI_API_KEY — the screen and extraction models.
  • OPENROUTER_API_KEY — required: the screen's first voter (deepseek/deepseek-v4-flash) routes through OpenRouter, as does any model whose id contains a "/" (see the constants in shared/config.py).
  • SUPABASE_SERVICE_KEY — required by every claimed --run. The claim is what stops two machines paying for the same works. SUPABASE_URL ships in .env.defaults.
  • HF_TOKEN — the pool and cache repositories on Hugging Face are private. Alternatively, run hf auth login once.

Use the project venv (.venv). Then pull the shared artefacts instead of recomputing them:

python -m shared.cache_sync --pull     # the shared API and LLM caches
python -m search.pool_sync --pull      # the ~7 GB survivor pool and its provenance sidecar

3.1 Stage 1 — only when the corpus itself must change

python -m search.run_search --scan

This scans the full 725 GB OpenAlex snapshot and takes many hours. Run it on an EC2 instance in the snapshot's own region, so the data transfer stays local; the runbook is docs/aws-snapshot-scan.md. The --scan flag is required precisely so nobody starts the scan by accident. Normally you pull the pool instead (section 3.0).

3.2 Stage 2 — route, screen, hand off

python -m filter.engine route          # runs the rule book → a NEW release; note its id
python -m filter.engine status         # lists all releases and their pile counts

The store holds many releases, so every release-bound command refuses to run without --release. Use --release latest for the newest release, or name one — a unique prefix is enough (--release 16d3). The current release is 16d370746b45 (a re-route after any filter-spec change mints a new one — the tier refuses a release whose spec bundle has moved, and says so).

python -m filter.engine screen --tier screen_expensive --release <id>        # dry run: cost estimate
python -m filter.engine screen --tier screen_expensive --release <id> --run  # the real screen
# Changed screen code? Sandbox a small batch first — same semantics as Stage 3's sandbox:
python -m filter.engine screen --tier screen_expensive --release <id> --run --limit 20 --mode validation

Without --run, screen is a dry run: it prints the row count and a cost estimate, and spends nothing. That is the whole stage: Stage 3 reads the screen's verdicts straight from the store. To export a release's screened rows as a reviewable CSV, run python -m filter.engine export-csv --out <file> --release <id> (it writes a manifest sidecar naming the release and row count).

3.3 Stage 3 — extract, then export

The tier and the export also refuse without --release. One general rule: the first run of changed code should go through the sandbox, so results can be evaluated without corrupting real output. The sandbox is --mode validation on both commands below: its verdicts are real but stored under that mode label, which the live export ignores. Promoting a good sandbox run is just re-running live — near-free, because every LLM call is cached.

# Sandbox first, if any Stage 3 code, prompt or model changed:
python -m extract.tier --release <id> --run --mode validation
python -m extract.export --release <id> --mode validation --out data/extracted-test.csv
# Read the sandbox rows before going live.

python -m extract.tier --release <id>             # dry run: worklist size and cost estimate
python -m extract.tier --release <id> --run       # the real run: claim → ladder → one verdict per work
python -m extract.export --release <id>           # verdicts → data/extracted.csv (whole file, atomic)
python -m extract.export --release <id> --check   # read-only: diff the store against the file
python -m extract.sanity_check                    # integrity report over the exported CSV

Run sanity_check after every export: a read-only report over the whole CSV — schema, cross-field contradictions, and (with --deep) two network checks.

What a re-run does, and does not, redo:

  • The worklist is rebuilt between batches. It subtracts settled works, works on the skip lists, works held on a current-generation target_pending, and anything the named release does not admit. api_error retries at once. A target_pending work is held indefinitely — re-running the same evidence re-buys the same answer — until --redo/--redo-status names it or a generation bump reopens it.
  • --redo W1,W2 re-extracts named works and supersedes their old verdicts. --redo-status names a population by its stored verdict status or link method instead (e.g. --redo-status no_original_found).
  • Editing a prompt or a model mints a new generation, which reopens every work at once. Do this knowingly. Two things soften the cost. First, the LLM cache: when an edit provably cannot change any answer (a typo, a renamed category), the maintainer can declare the old and new cache keys equivalent — freeze the pre-edit prompt version as a literal, register it in a module-level legacy-keys constant next to the call site, and read the cache through read_cache_migrating() in shared/cache.py, which substitutes only the declared component and re-files legacy hits under the current key with a provenance note. The existing answers then keep serving, and the declaration stops matching by itself as soon as anything else about the call changes. The worked example is _CLASSIFY_LEGACY_KEY_PARTS in shared/llm_client.py; the full recipe (including the generation-fingerprint side of it) is in CLAUDE.md, "Editing a prompt without invalidating its cache". Second, even without a declared equivalence, only the calls the edit actually touches miss the cache; everything else on a reopened work replays free.

3.4 Stage 4 — watch

python -m validate.app          # dashboard at http://localhost:5001

3.5 Hand over to validation

Give data/extracted.csv to the flora-validation repository. Its csv_to_db.py inserts the rows into the three Supabase validation tables in one idempotent transaction (ON CONFLICT (pair_id) DO NOTHING). Only rows with a settled outcome and a paper type are ready — 1,900 of the current 2,602.

3.6 What a run costs

  • Screening: measured on the current release, about $2 of DeepSeek for the whole 7,760-work pile (9.0M input / 1.8M output tokens at effort low), with the gpt-5.4-mini voter served largely from cache and the rest inside the OpenAI free budget. DeepSeek is half price off-peak (outside 01:00–04:00 and 06:00–10:00 UTC) from 2026-08-16. The dry run prints a list-price estimate that assumes no cache; read it as the ceiling.
  • Extraction: about $5 per 1,000 works when everything is bought fresh (measured: 1,325 works for $6.06; the dry-run model in extract/tier.py agrees in magnitude). A re-extract under a new generation is cheaper: only the calls whose prompts changed are re-bought, everything else replays from cache. Full-text rows dominate their own cost (about $0.012 per row for the PDF parse).
  • The OpenAI free budget is 9.5M tokens per day, a hard pre-call cap that resets at midnight UTC. Under the current outcome-policy generation, a full free window covers extraction of roughly 1,000–2,000 works (the outcome-family calls are the token-heavy part); the ledger does not attribute tokens per stage, so this is rough.
  • OpenAlex bills credits per request, and not uniformly: id and DOI lookups are free, list queries cost 1×, free-text searches 10×, content downloads 100×. Title searches are why the search steps sit at the bottom of the Stage 3 ladder. Which budget binds depends on the day's mix: a search-heavy campaign exhausts OpenAlex credits first, an extraction-heavy one hits the OpenAI cap first. A re-extract's DOI verification replays from cache, so its OpenAlex bill is near zero.
  • Estimate before you spend. Both stages print a dry-run estimate; read it first. While we confirm the budget, only Lukas should spend Gemini and OpenRouter tokens (they cost real money) beyond very small test runs.
