FLoRA Extractor — Screening Pipeline Audit

Behaviour, LLM call inventory, intent-vs-code divergences, bugs, and proposed fixes. Branch fix/track-decision-models @ 2d5b635 · audited 2026-07-28 · select any text to comment or suggest an edit.

TL;DR. The pipeline works broadly as designed, and the Stage-4.5 reference screen does most of the filtering work. But the screen is also where the design has drifted furthest from its documentation, and it sits downstream of a Stage-2 filter that admits roughly half non-replications.

Five confirmed bugs: Stage-4.5 successes never reach the validation DB (B1); any LLM failure during the screen is recorded as a "model disagreement" (B2); the 285 discarded and 125 set-aside rows carry no model attribution or evidence (B3); empty parse caches poison later fulltext outcome coding (B4); outcome-LLM exhaustion is laundered into cannot_be_determined (B5).

Two design concerns: the screen makes three LLM calls where two would do more work with better coverage (D1), and the Stage-4.6 title search writes resolved links at roughly 50% precision with systematic, not random, errors (D2).

One efficiency win that is essentially free: the screen's "is this a replication?" question fires fifth in the ladder, after two heavy-model calls have already been spent on rows that are then discarded (E1).

Root cause under both design concerns: Stage 2 admits an estimated 47–58% non-replications into Stage 3 (§5), and both D1 and D2 are downstream compensation for that. The estimate's weak point is that it rests on a classifier validated against eight hand-checked cases — which is why hand-coding the 125 set-aside disagreement rows is the highest-value next measurement.

1 · The pipeline, step by step (as the code actually behaves)

LLM calls are numbered L1–L13 throughout; each number links to its literal prompt in the appendix.

Stage 2 — filter

filter/run_filter.py · filter/rule_filter.py:44–138 · filter/llm_filter.py

candidates.csv is read in 50k-row chunks. The rule gate is first-match-wins:

  1. Non-article DOI (figshare, /reviews/, /decisions/) → false_positive, high.
  2. Exclusion pattern fires → the #44 rescue: if a replication phrase plus any author-year cite exists → needs_review, medium; otherwise false_positive, high.
  3. No replication phrase → false_positive, high (the ~2.17M-row bucket in docs/limitations.md).
  4. Phrase without a same-sentence cite → needs_review, medium.
  5. Phrase + same-sentence cite → replication / reproduction, high.

Only needs_review rows reach L1, whose verdict overwrites the rule status and confidence (filter_method="both"). On LLM failure the row is deliberately not written, so the next run retries it (#45).

Stage 3 entry — match-type routing

extract/run_extract.py:1259, :358–489

Per row, classify_match_type runs first: rule-based multi-original patterns (Many Labs, RRR, "replications of N"), then L2, cached at cache/llm/match_type_{key}.json. multiple_original rows go to the multi pipeline (L7), which never touches the reference screen at all. Everything else goes to run_for_doi().

Stage 4.5 in detail

shared/llm_client.py:1205–1290 · extract/link_original.py:665–739

  • Q1 (classify) — L4, run twice: the same prompt (title + abstract, no references) goes to two models — gemini-3.5-flash-lite and gpt-5-mini. Agreement requires both calls to succeed and return the same label; the weaker confidence governs.
  • Discard: agreed no at high confidence → not_a_replication; no PDF, no outcome call.
  • Q2 (target) — L5: on agreed yes with references, one call to gemini-3-flash-preview picks a numbered reference; accepted only at target_confidence == "high" → llm_references.
  • Disagreement: row set aside as screen_disagreement, not escalated.
  • Everything else (agreed unclear, medium/low no, yes with no target) falls through to the PDF stage.

Exit plumbing

_get_outcome (L8–L11) short-circuits only for not_a_replication; every other row — including screen_disagreement — runs an outcome call. sanity_check then routes first-match-wins: outcome == not_a_replication → not_a_replication.csv; non-article DOI; self-link; DOI mismatch; screen_disagreement → screen_disagreement.csv; target_pending.

Live distribution (489 cached screen results, verified directly): 58% agreed-no/high (discarded) · 22% disagreement (set aside) · 19% agreed-yes/high · <1% other. All cached results have two votes, so both providers were up during past runs.

3 · Bugs & proposed fixes

Ranked by severity. "Verified" = checked directly against code or on-disk data during this audit, not merely reported by a review agent.

B1 — Stage-4.5 resolutions never reach the validation DB severeverified

shared/schema.py:110–123 · extract/csv_to_db.py:208–209

llm_references is missing from RESOLVED_LINK_METHODS, and csv_to_db filters imports on that set. In data/extracted-test.csv, 43 of 172 rows (25%) are llm_references — all link_confidence=high, mostly doi_o_verification=verified — and all would be silently dropped. LINK_METHOD_VALUES is likewise missing llm_references, not_a_replication, and screen_disagreement, so the schema enum no longer covers what the pipeline emits.

Fix: add llm_references to RESOLVED_LINK_METHODS; add the two set-aside values to LINK_METHOD_VALUES; document all three in docs/csv-schema.md. Add a schema test asserting every link_method the pipeline can emit is in LINK_METHOD_VALUES, so the next new method cannot silently fall outside the enum.

B2 — LLM failure masquerades as model disagreement severeverified

shared/llm_client.py:1233–1250 · extract/link_original.py:704

One provider failing leaves a single vote; models_agree requires len(votes) == 2, so the row becomes screen_disagreement — even when the surviving vote was a high-confidence no. Both providers failing returns llm_refscreen_failed, which also has models_agree=False and is caught by the same branch — the target_pending mapping for it is unreachable. Single-vote results are cached and replayed on --resume. With no OPENAI_API_KEY (as .env.example ships), every screened row becomes a disagreement and nothing is ever discarded. The current cache shows 0 single-vote artifacts, so past runs are clean — but this is one outage away, and it would contaminate the agreement statistics the 2000-row brief asks to report.

Fix: distinguish three states: (a) both voted → real agreement/disagreement; (b) one vote → llm_refscreen_partial, do not cache, route to target_pending; (c) zero votes → llm_refscreen_failed, handled before the disagreement branch so it maps to api_error as documented. Fail fast at startup if only one screen provider is configured, and state the two-provider requirement in .env.example and CLAUDE.md.

B3 — Set-aside rows are unreviewable; decision models misattributed highverified

extract/link_original.py:685–693 · shared/llm_client.py:1245, 1266–1285

All 285 not_a_replication rows and all 125 screen_disagreement rows have empty link_llm_model; the discard path drops the screen's evidence and reasoning entirely. This directly defeats commit 2d5b635's goal ("every row answers 'what decided this?'"). Additionally, llm_references rows record the classifier pair (L4) as link_llm_model, but the model that actually picked the original was L5's — and L5's evidence_quote, the one quote that justifies the link, is requested in the prompt and then discarded.

Fix: pass the full screen dict (not a minimal literal) through _build_output on the discard path. After L5 resolves, overwrite llm_model with the target-picker model and llm_evidence with L5's evidence_quote. Also persist classify_llm_model from L2 — currently computed and thrown away, making routing the one decision with no attribution at all.

B4 — Empty parse caches poison later fulltext outcome coding highverified

extract/run_extract.py:657–683, :1331

_save_parse_cache is called for every non-multi row — including screen exits with no PDF — writing a parse cache of six empty results. It early-returns if the file exists, so if that DOI later does get a PDF, L9 still reads the stale empty cache and codes from the abstract only. 276 of 300 sampled cache/parse/*.json files contain no text in any method.

Fix: only call _save_parse_cache when the row actually reached the PDF stage, and treat an all-empty cached result as a miss. A one-off script should delete the existing empty parse caches.

B5 — Outcome API exhaustion laundered into cannot_be_determined high

extract/code_outcome.py:301–319, :380–390

After all retries fail, the outcome is recorded as cannot_be_determined/low with llm_model="" — indistinguishable from a genuine verdict, kept in extracted.csv, contradicting the CLAUDE.md api_error contract. The retry loop's exponential backoff is also dead code: call_llm never raises, so failure means ~9+ provider attempts with zero delay between outer retries.

Fix: return outcome = "api_error" when call_llm reports failure on all attempts, and sleep on the None-result path, not only in except.

B6 — Disagreement rows leak into not_a_replication.csv mediumverified

extract/run_extract.py:693 · extract/sanity_check.py:113,119

screen_disagreement rows still run an outcome call, which can return not_a_replication; the sanity-check outcome rule wins over the disagreement rule. 3 such rows are in data/not_a_replication.csv now — so "both models agreed it isn't a replication" is not quite true of that file, and hand-validation precision computed over it is biased.

Fix: solved for free by E2. Independently, move the screen_disagreement rule ahead of the outcome rule in sanity_check and re-route the 3 existing rows.

B7 — _FAILURE keywords misfire on successful replications medium

extract/code_outcome.py:78–88, :134–138, :412–429

"No evidence" / "no significant difference" are checked first and coded failure/high — but they are common phrasings in successful replications ("no significant difference between our estimate and the original"). This affects --no-llm runs and, worse, predict_outcome_keyword, which pre-filters which rows get processed at all under --predicted-outcome, silently biasing the sample.

Fix: require failure keywords not to co-occur with a success keyword in the same sentence, or drop the keyword pre-filter for sampling and use L4's output instead.

B8 — Match-type LLM failure cached permanently as single_original medium

extract/run_extract.py:419–422, :487–489

The L2 cache is written unconditionally, and the failure default is {single_original, low}. A Many Labs paper hitting a 429 (whose title doesn't trip the rule) is frozen as single_original for all future runs.

Fix: cache only on LLM success, as llm_filter and _llm_outcome already do.

B9 — Stage-4 abstract LLM defeats its own self-link guard medium

extract/link_original.py:653 · shared/llm_client.py:653

doi_r + "_abstract" is passed as both cache key and exclude_doi, so the "never link a paper to itself" exclusion never matches a real DOI on the L3 path. _guard_original_link catches it downstream, but the row is then downgraded to target_pending instead of resolved correctly.

Fix: separate the two parameters — pass the real doi_r as exclude_doi and a distinct cache-key suffix.

B10 — Set-asides are frozen; multi-original rows mislabelled low

extract/run_extract.py:818–830, :628, :1315

--resume never revisits not_a_replication / screen_disagreement rows, so fixes to B2/B3 will not reprocess them without manual CSV surgery. Separately, multi-original reproductions get hardcoded type="replication" and are validated against the wrong outcome vocabulary; they also never record an outcome model even though it is known.

Fix: add the set-aside methods to the stale-artifact rescue in _load_extracted_rows (or add a --rescreen flag); honour filter_status in _merge_multi_row.

4 · Design concerns

These are not defects in the sense that the code fails to do what it was written to do. They are places where the design itself is worth revisiting — one about cost and coverage, one about precision.

D1 — The screen's call structure buys agreement on the cheap question only design

shared/llm_client.py:1205–1290 · commit 3f21862 (PR #82)

The screen was a single combined call until PR #82 split it into L4 (Q1, run on gemini-3.5-flash-lite and gpt-5-mini) plus L5 (Q2, one call to gemini-3-flash-preview), with the outcome (L8) as a separate downstream call as it always was.

What the split actually costs, measured on the 489 cached screen results:

Screen outcomeN% of screenedCalls
Agreed "no" (discard)28658.5%2 (L4×2)
Disagreement (set aside)10721.9%2 (L4×2)
Agreed "yes"9619.6%2, +1 if refs exist
Q2 actually fired6813.9%3
Q2 resolved a target at high confidence438.8%—

Correction to the framing: "three calls per positive row" holds for only 14% of screened rows. The dominant cost of the split is not Q2 — it is that the second Q1 vote runs on 100% of screened rows. Average is ~2.1 calls per screened row, not 3.

The split's stated reasons, assessed:

  • The shared confidence field was a real defect — the commit message documents it clearly (a high-confidence negative was "barely expressible" while the discard path required exactly that). But it is fixed by returning two confidence fields, not by making two calls.
  • Contamination of Q1 by an attractive candidate reference is the only argument that genuinely requires separation — and it was never measured. PR #82 shipped on eight hand-checked cases.
  • Not sending reference lists to obvious negatives is a genuine and larger saving than it sounds: references are now withheld from the 86% of rows that never reach Q2, not merely from the ~45% that are clear negatives.

What is genuinely missing today: the two-model agreement rule applies only to Q1. The target pick (L5) and the outcome (L8) are both single-model decisions with no second opinion — and those are the two that write a database record, whereas Q1 merely discards.

Proposed: one combined call asking (1) replication / reproduction / neither, (2) the target, (3) the reported outcome where the abstract states it — run on both models. Two calls per row, flat; the "two models must agree to discard" property is preserved; and the target and outcome each gain the second opinion they currently lack. Keep classification_confidence and target_confidence separate, since the discard threshold and the write threshold are different bets.

Honest counter-argument: this is close to call-neutral (~2.1 → 2.0) and is a token increase, because the reference list would go to 100% of rows instead of 14%. The case for it rests on coverage — getting a second model onto the two write decisions — not on cost. Judge it on that basis.

Measure first: run combined vs split on a few hundred rows and compare Q1 verdicts. That tests the contamination claim PR #82 asserted but never validated, and it is the one result that would justify keeping the calls separate.

One supporting claim did not survive checking. The proposal was partly motivated by abstract-only outcome coding on title-declared replications reportedly yielding 14% success / 57% mixed / 29% failure with descriptive at zero. The actual distribution over all 556 such rows (title_r matching /replicat/i, out_quote_source == "abstract") is 44.8% success · 19.1% failure · 17.1% mixed · 14.6% cannot_be_determined · 3.8% descriptive. No subsetting I tried reproduced the quoted figures. The real distribution is success-heavy, which is a reason for caution about abstract-only outcome coding rather than reassurance — and it connects directly to the success-over-calling concern in D2.

D2 — Stage 4.6 title search: ~50% precision, with systematic errors design · accuracy

extract/link_original.py:508–538 · shared/schema.py (llm_title_search note)

When the screen names a target it cannot match to a reference, the pipeline searches CrossRef/OpenAlex for that title and writes the result as a resolved link (link_method = llm_title_search). This is the one resolved link method where the target is not selected from a supplied enumerated list — there is no bounded candidate set constraining the answer, so a plausible-sounding title can be matched against the whole literature.

Precision of characterisation: "the LLM invents the reference from memory" is fair for the post-PDF path (llm_title_search_gemini/_openai, shared/llm_client.py:646–660), where the model emits a free-text title when the target is absent from the candidate list. It is not fair for Stage 4.6 itself: L5 instructs the model to "copy the identifying wording into target_description … as the abstract states it", so that string is a transcription from the abstract, and the DOI comes from a real search. The substantive risk — an unbounded match — is identical either way.

Hand-check of all 13 such rows from the 2026-07-28 batch: 6 correct, 5 wrong, 2 borderline. An independent re-read during this audit gave roughly 4–5 clearly correct, 3 clearly wrong, and 4–5 borderline — consistent in magnitude ("roughly half right"), though not with the exact 6/5/2 split. The correct ones are genuinely valuable and nothing else in the pipeline would catch them: a mental-timeline replication was linked to Time (also) flies from left to right, and a foreign-aid replication to its exact target. But the errors are systematic rather than random — a paper that is not a replication gets confidently linked to a landmark it merely cites: an ABCA7 expression conference abstract to a 74,046-person Alzheimer's GWAS meta-analysis, a hamster challenge experiment to a population-level SARS-CoV-2 transmissibility estimate, an AML transplant analysis to a JCO commentary its target_description did not describe. An outcome is then coded against that pairing, feeding the success-over-calling problem.

The DOI-verification safety net cannot catch this. All 13 rows carry doi_o_verification == "verified", and 7 of 13 carry link_confidence = high — including two of the questionable ones. Verification confirms that the DOI resolves to the named title; it has no way to detect that the named title is the wrong target. This failure mode is structurally invisible to every automated check currently in the pipeline.

Yield across the 601 rows Stage 3 processed in this batch: 13 links produced (2.2% gross), of which roughly 6 are correct (~1% net). Note that data/extracted.csv holds a further 50 llm_title_search rows from the older post-PDF path, which have never been hand-checked.

One sub-claim needs restating. One of the correct catches does have an "A Replication of X" title that matches Stage 2.5's patterns — but Stage 2.5 could not structurally have caught it: _resolve_by_title_pattern needs a candidate pool to match against, and that row's pool was empty. That is an argument for giving Stage 2.5 a title-search fallback for its own extracted target, not evidence that Stage 4.6 is redundant.

Proposed: don't delete the step, gate it. Run it only when the screen returns high confidence, and record the result as provisional — requiring human confirmation rather than writing it as a resolved link with an outcome attached. That retains the genuine catches and stops the step manufacturing links for papers that should never have reached it.

This interacts with B1 in a way worth stating plainly: llm_title_search is in RESOLVED_LINK_METHODS and therefore imported into the validation DB at ~50% precision, while the better-evidenced llm_references is not imported at all. The two are exactly backwards.

Provenance note on the in-code claim that every doi_o mismatch in the 2026-07 audit came from this path (shared/schema.py:119–122): the audit found 43 mismatches, all labelled link_method=llm_fulltext at the time — llm_title_search was created by that same commit to separate the sub-path out. The attribution is a root-cause inference, not a measured per-row breakdown, and data/doi_audit_report.csv has no link_method column to re-derive it. The mechanism is well argued; the phrasing should be "the audit's 43 mismatches were all llm_fulltext rows, and the root cause was traced to the title-search branch."

5 · The shared root cause

D1 and D2 are both downstream compensation for the same upstream problem: Stage 2 admits a large fraction of non-replications into Stage 3. The screen exists to catch them, and the title search exists to rescue targets the screen could not match — neither would carry so much weight if the input were cleaner.

Quantifying it, with the selection effect handled explicitly. The headline "58% of screened rows are discarded" is measured on a biased subsample: only rows that failed stages 2.5–4 reach the screen, and rows resolving early are disproportionately genuine replications. Correcting for that:

So Stage 2's false-positive rate among rows reaching Stage 3 is bounded below by 47.4% and plausibly sits near 56% (counting half the disagreements as negatives), with 65% as the ceiling. A "~45–55%" estimate is well supported; 58% is not the right point estimate to quote — it is the rate within the screened subset only.

The selection worry turns out to be smaller than it first appears, for a structural reason: stages 2.5–4 all require find_all_candidates() to return something, which requires a parseable (Author, Year) citation. In this batch those stages fired on nothing at all — there are zero title_pattern_match, citation_context_match, same_author_year_title_overlap, and single_candidate_after_requery rows. Only Stage 4 resolved anything early (74 rows). So the screened subset is 81% of the batch and is only mildly enriched; the worst-case gap between the two rates is 11 points.

The real weakness in this estimate is not selection bias — it is the instrument. The 285 discards are an LLM verdict, and L4 was validated on eight hand-checked cases (PR #82). A headline "Stage 2 admits half non-replications" currently rests on that. Two further caveats: this batch comes from --extracted-test, which skips DOIs already resolved in extracted.csv, so it is drawn from a harder residue and the rate is likely biased upward; and the 107 disagreements are the genuinely informative cases and sit unadjudicated.

Implication for triage: neither the D1 restructure nor the D2 gate removes the need to address Stage 2 precision directly — every LLM call in the ladder is spent at roughly 2× the necessary volume because half the input should not be there.

The single highest-value next measurement is to hand-code a sample of data/screen_disagreement.csv (125 rows). It would tighten the 47–58% range more than anything else available and give L4 the validation it currently lacks — one exercise resolving both weaknesses. docs/limitations.md covers the opposite error (phrase-gate false negatives); the precision side has no equivalent write-up and should get one.

6 · Rate limits, model choice, and cost

Measured on 2026-07-29 from the account's own AI Studio dashboard (Google no longer publishes static limit tables — the docs page defers to a per-project view). Third-party sites quoting "1,500 RPD" for the free tier are wrong by roughly two orders of magnitude.

20 requests per day on the heavy model is the binding constraint. A single row costs 1–4 heavy calls as it escalates the ladder, so the free tier sustains roughly 5–20 rows per day — a 2,000-row run would take months. This, not key rotation, is why the 2026-07-28 run exhausted quota. Note the 25× asymmetry: Flash-Lite gets 500 RPD against Flash's 20, so putting the highest-volume call (L4) on the light model was the right decision.

Fix: enable billing (Tier 1 — instant, $250 cap). It raises the heavy model to 10,000 RPD, a 500× increase on the binding limit.

Key rotation does not substitute. Google's docs state plainly that "rate limits are applied per project, not per API key," so multiple keys in one project share one bucket — CLAUDE.md:410 describes GEMINI_API_KEY_2 as "key rotation for higher quota", which only holds if the keys belong to separate projects. Sharding one workload across projects to multiply free quota is also the kind of thing Google's terms treat as abuse, and 5 projects × 20 RPD still would not run the pipeline.

Loader

def render_prompt(name: str, **fields) -> tuple[str, str]:
    """Render prompts/<name>.md with fields; return (prompt_text, version).

    version = first 12 hex chars of sha256 over the fully-expanded template
    (partials included), so editing a shared partial invalidates every prompt
    using it. Callers MUST fold version into their cache key.
    Raises KeyError on a missing placeholder — a missing field is a silently
    degraded prompt, not a blank line.
    """

Templates are plain Markdown with {named} placeholders and one {{include:_partials/…}} directive; str.format gives missing-placeholder errors for free. This collapses the 2×2 outcome grid into a single formatted path name and deletes four Python functions.

Cache-key integration (the part that must not be got wrong)

The returned version replaces every hand-maintained constant (PROMPT_VERSION, REF_SCREEN_PROMPT_VERSION) and fills the fourteen gaps. Two consequences to accept deliberately:

  1. Editing a template invalidates its cache. That is the point — today an edit silently reuses answers produced by the previous wording unless someone remembers a manual bump. Land the first deployment with a one-off rekey script for entries whose template text is provably unchanged.
  2. LLM_CACHE_READ=accumulate must go (see E3), or the version fold is dead on arrival for the outcome cache.

The audit benefit is visible in this document: with prompts as files, git log -p prompts/extract/screen_is_replication.md becomes the complete revision history of the classifier that discards 58% of screened rows — including the PR #82 split that D1 revisits. Today that history is interleaved with unrelated changes across 1,290 lines of llm_client.py.

12 · FLoRA coding rules vs the pipeline

Sources: the FLoRA project document (Aim / Coding Level / Inclusion Criteria / Columns & Codebook / Excluded articles) and forrtproject/fred-data · output/flora_faq.md. The Columns / Codebook table in that document is the spec — where the shipped flora.csv disagrees with it, the table wins; those disagreements are catalogued separately in §13. Each item below states the database rule, then what the code does. Nothing here has been changed — these are the points where the two would produce different entries, so that the team can decide which side moves.

Severity is about database consequence, not code quality: severe = the pipeline would emit values FLoRA cannot accept, or drop entries FLoRA wants; moderate = systematic mis-coding within accepted values; minor = an unimplemented field or a wording gap.

12.1 Outcome vocabulary

R1 — The reproduction grid has the wrong number of levels on both axes severe

shared/schema.py:172–182 · shared/prompts.py:580–608 · codebook rows outcome_computational / outcome_robustness

The codebook defines five computational levels — Precise · Minor deviations · Major deviations · Uninformative / technical failure (no code, no data, did not try) · Not checked — and four robustness levels — Robust · Minor challenges · Major challenges · Not checked. The pipeline emits a 3×3 grid: computationally successful | computational issues | computation not checked × robust | robustness challenges | robustness not checked.

So the pipeline collapses minor and major on both axes, and has no value at all for uninformative / technical failure — the case where reproduction was attempted but no code or data existed. That last one is not a rounding difference: it is the most common real reproduction outcome in economics, and the pipeline must currently record it either as "computational issues" (wrong — implies the numbers differed) or as cannot_be_determined (wrong — implies the coder could not read the paper).

The project document also floats the ACRE/BITSS 10-level scale as an alternative. Three vocabularies are in play; the pipeline implements a fourth.

Decision needed: which vocabulary is canonical. If the codebook's, the schema grid becomes 5×4 = 20 strings plus the technical-failure escape, and REPRO_OUTCOME_RULES needs the minor/major boundary defined in words a model can apply consistently.

R2 — Two separate coded axes, each with its own quote, are stored as one joined string moderate

shared/schema.py:172–182 · shared/prompts.py:610–618

The codebook has four columns: outcome_computational, outcome_computational_quote, outcome_robustness, outcome_robustness_quote. The pipeline writes one outcome string ("computational issues, robust") and one shared outcome_phrase. A validator therefore sees a single quote that has to justify two independent judgments, and any downstream analysis of one axis has to re-split the string.

Fix if the codebook stands: split into two coded columns and two quote columns in EXTRACT_ADDED_COLS and in the repro prompt's JSON block; keep the joined string only as a display convenience.

R3 — "Statistically successful but flawed" is a FLoRA outcome the pipeline cannot emit severe

shared/schema.py:156–161 · shared/prompts.py:552–565

The codebook's replication outcome list is Success · Failure · Mixed · Uninformative · Statistically successful but flawed · Descriptive / not applicable. The pipeline's OUTCOME_CATEGORIES is success · failure · mixed · descriptive · cannot_be_determined · not_a_replication.

"Statistically successful but flawed" (the codebook's example: "we replicated x using the original methods, but show that they are not a valid test of the hypotheses") has no representation. Under the pipeline's rules such a paper codes as success — the authors do report the effect was obtained — which is the reading FLoRA specifically created a separate category to avoid.

Applied (PR 10): added as statistically_successful_but_flawed to OUTCOME_CATEGORIES and to OUTCOME_RULES with the codebook's own example. Every outcome JSON block now interpolates one shared OUTCOME_ENUM string: a category defined in the rules but missing from the enum is silently coerced away, and the abstract, fulltext and multi-original prompts had already drifted apart on exactly that.

R4 — uninformative is a live FLoRA category that the pipeline retired as legacy severe

shared/schema.py:190–192 · shared/prompts.py:559

FLoRA's Uninformative means something specific: the replication authors themselves say the study cannot speak to the original (e.g. their sample was too small). The pipeline lists uninformative under OUTCOME_LEGACY_VALUES — "predates cannot_be_determined" — and folds it into cannot_be_determined, whose prompt rule explicitly covers both readings: "either it lacks the information, or the authors themselves report the result as inconclusive".

Those are different facts about the world. One is a property of the paper (an underpowered replication is a finding); the other is a property of our extraction (we could not tell). Merged, the database can no longer distinguish a null-informative replication from an unread one, and any "share of replications we could not code" statistic silently includes papers that were coded correctly.

Applied (PR 10): uninformative is a first-class category again with the codebook's definition, OUTCOME_LEGACY_VALUES is empty, and cannot_be_determined is narrowed in the prompt to "WE cannot tell from the text supplied". One consequence beyond the prompt: supabase_client._OUTCOME_CANON was folding uninformative into cannot_be_determined before building the pipeline-vs-human confusion matrix, so a human correcting one to the other landed on the diagonal and read as agreement. It no longer does. The outcome cache is invalidated by the prompt-hash keys automatically.

R5 — not_a_replication is written into the outcome column minor

shared/schema.py:156–161 · extract/code_outcome.py:246–248

FLoRA has no such outcome — a paper that is not a replication is not an entry. The pipeline uses the outcome column to carry an exclusion decision, then relies on sanity_check to quarantine those rows. It works, but the column now mixes "what happened in the replication" with "this is not a replication", and any consumer reading extracted.csv without applying the quarantine rules sees a value the codebook does not define.

12.2 What counts as a replication

R6 — "Replication must be an AIM, not a RESULT" is enforced in Stage 2 and absent from the Stage-3 screen severe

shared/prompts.py:71–73 (Stage 2) vs 456–485 (Stage 3 front door)

This is FLoRA's headline inclusion criterion, capitalised in the project document: self-identification as a replication before the results, as a statement of purpose. The Stage-2 filter prompt carries it — "Must intend to replicate a specific prior study…; it is not enough to report that findings replicate earlier work."

The Stage-3 front-door screen (L4), which discards 58% of rows and is the gate whose verdict is written as the final answer, defines it differently: "A paper is a REPLICATION if it collects new data to re-test a finding reported in a previously published study." That admits papers whose replication is a result, and it is the looser of the two definitions applied later in the pipeline — so a paper Stage 2 correctly held at needs_review can be waved through by the screen on the wider rule.

Fix: port the aim-not-result sentence into _CLASSIFY_PROMPT verbatim. Cheap, and it makes the two gates agree on the construct they are both gating.

R7 — "A study or experiment, not an association or finding" appears nowhere in the code severe

shared/prompts.py:71, 458–462 · the project document's inclusion criteria and the "tangential claims" exclusion

FLoRA excludes papers that replicate an association or a finding rather than a study, and the document names worked examples on both sides (10.1073/pnas.2103313118 in, 10.1177/0956797619831612 out) plus the Soto-type papers as a class. The FReD→FLoRA comparison table sharpens it further: checked claims "must be central", where FReD accepted tangential ones.

Every prompt in the pipeline is written in exactly the opposite vocabulary: Stage 2 says "re-test a finding from a previously published study", the screen says "re-test a published finding", and no prompt mentions centrality at all. There is no rule anywhere that would exclude a paper for re-testing a peripheral association.

This is the largest single gap between the two rule sets, and it is upstream of everything else: it changes which papers are entries at all, not how they are coded.

Needs a decision before it can be a fix. "Central claim of a specific study" is a judgment the worked examples make operational for a human; it needs to be written as rules a model can apply, ideally with those same DOIs as few-shot cases.

R8 — Meta-analyses are a blanket false positive; FLoRA includes some of them moderate

shared/prompts.py:90 · FAQ, "Can meta-analyses that replicate previous meta-analysis also be included?"

The FAQ answers yes: a meta-analysis that re-runs an earlier meta-analysis on different data (e.g. a larger set of studies) is a replication. The Stage-2 filter prompt lists "meta-analyses or systematic reviews" as a false_positive type with no carve-out, so these are rejected before Stage 3 ever sees them.

R9 — Overlapping observations: the document allows them, the filter prompt's key criterion forbids them moderate

shared/prompts.py:70–87 · document §Replications vs Reproduction · FAQ, "additional decade of data" and the panel-data rule

FLoRA: "Replication has different observations (can be overlapping); reproduction has the same observations." The FAQ confirms it — an extra decade of data on the same series is a replication, and panel-data replications that reuse the original's earlier waves still count.

The filter prompt states the criterion without the overlap allowance: "Key criterion: the observations analysed are not the original's." It does partly compensate — later waves and same-repository samples are listed as replications — but the stated rule and the examples pull in opposite directions, and a model that follows the stated rule will code overlapping-sample panel replications as reproductions.

Fix: one clause — "the sample may overlap the original's, as long as it adds observations the original did not analyse".

R10 — None of the report-type exclusions are implemented moderate

shared/utils.py:68–83 · filter/rule_filter.py:52–60

FLoRA excludes: registrations (cannot be linked to a publication, risk duplication), reports hosted on Google Docs, and non-persistent websites/blogs such as Psychfiledrawer — while explicitly allowing Zenodo, OSF and RPubs. It also requires a narrative summary rather than a post-completion registration or a bare results table.

The pipeline's only structural exclusion is non_article_doi(): figshare DOIs and peer-review objects. OSF registrations in particular are not distinguished from OSF reports, which is the exclusion FLoRA calls out first.

The two source documents disagree with each other here: the project document lists "blog posts on websites, RPubs" as acceptable report types, while the FAQ's quality criteria exclude blog posts as non-persistent. Worth resolving upstream before implementing either.

R11 — Psychometric and LLM-respondent exclusions have no rule minor

document §Special types · §List of Excluded articles

Two named exclusions with no counterpart in any prompt: psychometric papers are in only when they replicate previous claims, not patterns such as a factor structure; and a "replication" whose respondents are LLMs is excluded (ideas.repec.org/a/beh/jbepv1/v9y2025i1p75-80.html). Both are narrow, and both are the kind of case the screen will confidently accept.

12.3 Row level and identifiers

R12 — study_o is a study number in FLoRA and a title in the import severe

extract/csv_to_db.py:117

The codebook defines study_o as "Target study in original ref — study number, can be multiple (e.g. 1, 2)", coded from the replication's abstract. csv_to_db writes "study_o": _s(row.get("title_o")) — the original paper's title.

Whatever the Supabase column means today, the pipeline never extracts a study number at all, so the FLoRA coding level ("one row is one pair of references; if one replication targets several studies within the same original paper, it stays one row and study_o carries several values") cannot be represented. Multi-target papers are instead always expanded to N rows keyed by original_rank — correct for N distinct original papers (the document's "combinations of two prior studies" rule), wrong for N studies inside one paper.

Applied (PR 10), partly: extracted.csv has a real study_o column, the multi-original prompt asks for a study number per targeted study, and _collapse_same_paper_originals() groups entries that share an original paper into one row with the numbers joined ("1, 2"), aggregating their outcomes the way the FAQ says to — conflicting verdicts become mixed, a silent study never outvotes one that reached a verdict. That also fixes a duplicate-key bug: entries sharing a doi_o produced two rows with the same pair_id.

csv_to_db now sends titles as title_r / title_o and study_o as the number: study_r / study_o are study identifiers, never titles. This blocks the import until the validation repo adds the two title columns — every insert fails with a PostgREST "column does not exist" error, so nothing is written and nothing is corrupted, but nothing imports either. The cross-repo change and the in-repo readers that still treat study_r as a title are tracked in issue #103.

R13 — A paper that is both a reproduction and a replication yields one row moderate

extract/run_extract.py:816–820 · FAQ, "What if a paper includes reproduction and replication?"

FLoRA lists it twice — once as each. The pipeline derives record_type from a single filter_status value and codes one row in one vocabulary; there is no path that emits both. The half that loses the coin toss is simply absent from the database.

R14 — No preprint / version-of-record handling, and no meta-paper identifiers moderate

shared/schema.py:37–77 · FAQ, "How are you dealing with Preprints?" and "How are meta-papers treated?"

FLoRA codes the version of record in doi_r and keeps preprints and other versions in alt_id_r / alt_id_o; for meta-papers it prefers the individually published version in doi_r and records the meta-paper in ref_meta_r / doi_meta_r; url_r holds the individual report when the DOI points at a multi-study container. For originals it always takes the reference as given in the article.

EXTRACT_ADDED_COLS has none of alt_id_r, alt_id_o, ref_meta_r, doi_meta_r. Whichever record OpenAlex returned becomes doi_r, with no preprint→published resolution. For Many Labs-style corpora — a large share of what FLoRA contains — this means the meta-paper DOI lands in doi_r for every row, which is exactly the case the FAQ writes a rule against.

R15 — Three codebook columns are not produced at all minor

shared/schema.py:37–77

  • publication_status_r — the FAQ gives a mechanical rule (Crossref journal present → journal article; NA and "SSRN Electronic Journal" → working paper) that the pipeline already has the metadata for, in journal_r.
  • field — LLM-assisted classification against the DFG taxonomy; not implemented.
  • Entry source — the codebook's vocabulary is "Submission, systematic search, …"; the pipeline's source uses openalex | semantic_scholar | …. Not wrong, just a different axis, and something has to map one to the other.

Also worth a decision: the codebook marks abstract_r "for future analyses — not to be published", and csv_to_db writes it into the unvalidated table.

12.4 Where the outcome is read from

R16 — The escalation reads the first 8,000 characters; FLoRA's rule points at the discussion and conclusion severe

extract/code_outcome.py:41, 276–277 · extract/run_extract.py:831–850 · FAQ, "What is the outcome based on?"

FLoRA: rely on the abstract; if the outcome is not stated there, use the discussion and conclusion sections. The pipeline's abstract-first design matches the first half exactly. The escalation does not match the second: _best_fulltext_from_cache() returns the winning parser's raw_text — the whole paper from page one — and _llm_outcome truncates it at _FULLTEXT_CAP = 8000 characters. For a typical article that window ends somewhere in the methods, so the sections FLoRA names as the authoritative source are the ones most reliably cut off, and the text that is sent is the introduction — which the module docstring itself warns "routinely discusses OTHER studies' failures".

Applied (PR 10): pdf_parsing.outcome_text() slices from the last discussion/conclusion heading to the reference list, and falls back to the closing pages before the references when there is no usable heading. The references boundary was already solved — grobid._split_sections() finds it by heading (last match, so an in-text "References show…" cannot win) with a fallback that walks paragraphs backwards for a dense block of APA-pattern lines. Two guards: a "Discussion" heading in the first 40% of the body is a structured abstract's own label rather than the section, and a heading with under 300 characters under it is a contents entry. The text carries a SOURCE: line so a quote is never attributed to a section the model was not shown.

One thing this turned up: _best_fulltext_from_cache() took the top-scoring parse method's raw text, but GROBID scores highly on references and returns no raw text at all — so it fell back to that method's abstract + intro while another method's full parse sat unused in the same cache. It now takes the best method that actually has raw text.

12.5 Coding rules the FAQ states and no prompt does

Each of these is a one- or two-sentence addition to OUTCOME_RULES. None is implemented; all would change codings today. Grouped here rather than given findings of their own because they share a single fix.

FLoRA ruleWhat the pipeline does instead
A failed manipulation check — so the hypothesis could not be tested — is coded failure. Same for a failed preliminary test. No rule. The prompt's cannot_be_determined definition ("the authors report the result as inconclusive") is the closest match and would usually win.
If the replication's title focuses on one specific effect and that effect did not replicate, code failure regardless of other successful checks. No rule. The prompt's mixed definition ("some of several tested findings replicated and others did not") points the other way.
Close replication works, conceptual replication does not → mixed. Reachable, but only via the authors'-own-framing test; the FAQ states it as a coder rule that applies however the authors frame it.
The outcome is about the central finding the replication was designed to test and "may leave out robustness checks and exploratory analyses". No rule. Any set of partly-supported findings, central or exploratory, reads as mixed.
A replication paper with several studies against one original: results are aggregated (authors' judgment; conflicting results → mixed). No rule for the one-original case. The multi-original prompt says the opposite for its own case — "look for the result for THAT SPECIFIC study, NOT the overall aggregate" — which is right there but reads as a general instruction.
Replication chains: link to "most likely the closest successor study". No rule. The identification prompt asks for "the ORIGINAL STUDY" and forbids picking the most prominent or most cited — which is the right instinct but does not say nearest predecessor.

12.6 Where the two already agree

Recorded so the audit is not read as one-sided, and so these are not "fixed" by accident:

  • Method replications are out. The screen prompt excludes evaluating or comparing an instrument or procedure as the study's goal — matching the document's excluded hal-05527295 ("replication" of a method).
  • Conceptual replications are in, as the document allows "for now".
  • Field-convention relabelling. The filter prompt's rule that an economics "replication" on the original data is a reproduction implements the document's observations-based split exactly.
  • Internal replications are out (Study 2 replicates Study 1) while a same-author replication of a published study is in.
  • Synthetic-data replications are included by the FAQ, and nothing in the pipeline excludes them.
  • Peer review is not required in either.
  • Descriptive / not applicable is defined in the prompt close to the codebook's sense.

13 · The shipped dataset vs the spec

The spec is the Columns / Codebook table in the FLoRA project document. There is no codebook file anywhere in forrtproject/fred-data — the only matches for "codebook" are in archived COS-report .qmd code, and release/ holds only the citation and dataset scripts. So §12 above measures the pipeline against that table, and this section measures the published artifact against it too.

Figures below are from output/flora.csv on main: 2,470 rows, 35 columns, 2,453 replications and 17 reproductions.

These are not pipeline bugs — nothing here is caused by this repo, and most of the rows predate it. They matter because the pipeline writes into this dataset: where the spec and the shipped file disagree, a compliant extractor produces values the file has no column for, or spells a category three different ways.

S1 — study_o does not exist in the published dataset severe

The spec's coding level — "one row is one pair of references; if one replication paper replicates multiple original studies from the same original paper, it is still one row but study_o has multiple values (e.g. 1, 2)" — is stated as the second heading of the project document, before the inclusion criteria. Neither study_o nor study_r is among flora.csv's 35 columns.

The codebook's own rightmost column, "Already coded for FReD 2.0 studies in FLoRA", is blank for study_o, so this is a planned field rather than a lost one. But it means the headline rule about what a row is currently has no representation in the artifact, and the pipeline's new study_o (R12) has nowhere to land — not in flora.csv, and not yet in the validation DB (#103).

The useful half of this table: statistically successful but flawed and uninformative are both real, populated values in the shipped data. R3 and R4 were categories the pipeline could not express that the database was already using — not categories invented from a design document.

S3 — 14 of the 17 reproductions have no outcome at all severe

Reproductions are 17 rows of 2,470 (0.7%). Three carry a grid value (computationally successful, robust / …, robustness challenges / …, robustness not checked — one each). The other 14 have an empty outcome, and they are essentially the whole of the file's 16 blanks.

So the reproduction half of the spec has been exercised three times. That is worth knowing before acting on R1: the 3×3-vs-5×4 mismatch has never been noticed because almost nothing has been coded on either grid, and the pipeline is about to become the first substantial producer of reproduction outcomes. Choosing the vocabulary now costs three rows of recoding; choosing it after a full run does not.

S5 — Eight codebook columns have no counterpart in the file moderate

study_o, publication_status_r, field, ref_meta_r, doi_meta_r, outcome_computational(+quote), outcome_robustness(+quote), abstract_r.

Consistent with the codebook being a design document: its "Already coded" column is ticked only for ref_o, ref_r, outcome, outcome_quote, out_quote_source and url_r. Two of these are the ones R15 asks the pipeline to produce — so producing them means adding columns to flora.csv, not just to extracted.csv.

Note that the two reproduction axes are among the absent columns, which is the other half of R2: the file stores the single joined outcome string, exactly as the pipeline does. On that point the shipped artifact and the pipeline agree with each other and differ from the spec.

S6 — outcome_quote_source is free text, not the specified vocabulary moderate

The codebook says "Page number or 'abstract'". The file holds 160 distinct values across 2,470 rows. 1,697 are abstract and a further 24 are Abstract; 119 look like page numbers. The rest include OSF report, full_text, Supplemental Infromation [sic], and bare URLs — data file at https://osf.io/fgjvw (76 rows), a GitHub issue comment link (62 rows), Study dataset at https://osf.io/4ewkh (25 rows).

Several of those are genuinely useful provenance the vocabulary has no room for. The pipeline emits a closed set (abstract | title | fulltext), so it will not add to the sprawl — but it also cannot record "OSF report", which is a real source for this corpus.

S7 — The preprint and meta-paper rules are barely exercised in the data minor

alt_identifier_o is populated in 14 rows and alt_identifier_r in 36, out of 2,470. Preprint versioning and meta-paper handling are the two longest answers in the FAQ, and the SCORE corpus alone (88 rows by source) is the case they were written for.

This does not change what R14 asks the pipeline to do; it does mean the pipeline would be the main producer of these fields rather than a late joiner to an established practice, so the rule needs to be operationalised, not merely followed.

13.1 What follows for the pipeline

  1. An export mapping is now a required piece of work, not a formality — S2 and S4. Three outcome values and three column names differ, in one direction only, with no existing code that does it.
  2. Settle the reproduction vocabulary before the next run (R1, S3). Three coded rows exist today; the cost of deciding late is proportional to what the pipeline writes between now and then.
  3. R3 and R4 are confirmed against data, not just against the spec — both categories are populated in flora.csv.
  4. Adding a column means adding it in three places (S1, S5): extracted.csv, the validation DB, and flora.csv. Issue #103 currently tracks the first two.
