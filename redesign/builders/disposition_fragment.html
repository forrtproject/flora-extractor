Review disposition — 30 applied, 37 open

Your 64 comments split into two piles. The 30 that were questions of wording with one defensible answer are applied in PR #89 and their threads on this page are resolved. The remaining 37 are below, grouped into 34 decisions (a few of your comments made the same point in different places), plus the three you raised this afternoon, each with what I think we should do.

Answer them here, not in the PR. Select any part of a recommendation and hit 💬 Comment to disagree, or ✏️ Suggest to rewrite the recommendation into the one you want. A one-word “yes” on the ones you agree with is enough — I will treat silence as undecided, not as consent.

Vocabulary and schema

Changes to what the pipeline records, not just how it asks. Each needs a migration decision.

D1 Relabel the rule-filter’s false_positive outcomes — L1

“Can we relabel these — not_an_article / false_positive_phrase / false_positive_no_phrase”

What it is: Three different rule paths all write the same false_positive, so the CSV cannot say why a row was dropped — a non-article DOI, an exclusion-pattern hit, and “no replication phrase at all” (the ~2.17M-row bucket) are indistinguishable after the fact.

Recommendation: Add a filter_reason column rather than splitting filter_status into more values. It answers the same question without touching the 3-way vocabulary that the dashboard, sanity_check and Supabase all key on.

D2 Rename filter_status → paper_type — L1

“rename to paper_type”

What it is: The field holds what kind of paper this is, not the state of any process — the name is wrong and invites the “is it done yet?” reading.

Recommendation: Agreed, but it is a pure rename across schema.py, every CSV, the dashboard and Supabase. Worth one mechanical PR with a migration — decide whether that happens now or waits for the next schema break.

D3 Code the reproduction outcome as two fields, not nine strings — L10/L11

“better to code this as 2x3? Would seem to make the prompt shorter and mistakes rarer”

What it is: The prompt currently lists nine exact strings the model must reproduce verbatim, and any deviation is coerced to cannot_be_determined by _normalise.

Recommendation: Agreed, and it is the strongest of the structural suggestions: ask for "computation" and "robustness" as separate keys with three values each, then join them in code. Same grid, a third of the prompt, and no way to emit an invalid string. Needs OUTCOME_CATEGORIES and any already-coded reproduction rows to follow.

D4 Add DOI/URL to extracted reference entries — L12/L13

“add doi/url field?”

What it is: The reference dicts carry authors/year/title only.

Recommendation: Cheap to add, but printed reference lists carry a DOI far less often than you would hope, and the downstream matcher resolves by title+author anyway. Low priority unless you have seen it fail on papers where the DOI was right there.

Prompt structure and consistency

Restructurings that should be measured rather than assumed — and one live mismatch (D13).

D5 Standardise the JSON block and return labels across prompts — all

“both the formatting of the JSON block and the return labels should be standardised across prompts”

What it is: Every prompt phrases its JSON instruction differently (“Respond with ONLY this JSON”, “Return ONLY valid JSON”, “Respond with only this JSON (no prose outside the braces)”), and confidence fields are variously confidence, filter_confidence, classification_confidence, target_confidence.

Recommendation: Now cheap to do, since every prompt is in shared/prompts.py. Propose one shared JSON_INSTRUCTION constant and one confidence vocabulary. The only real decision is whether renaming the response keys is worth invalidating the caches keyed on them.

D6 Put the genuine-attempt judgment first, since it is judged first — L8–L11

“Should “first” come first in the prompt?”

What it is: The block says “Before classifying the outcome, first judge…” but sits after the outcome rules and few-shot examples.

Recommendation: Agreed — move it above the outcome rules. Held back only because it changes every outcome prompt and I would rather spot-check ~50 rows before and after than assume it is free.

D7 Merge the abstract and fulltext outcome prompts — L8+L9, L10+L11

“merge with previous, so that we don’t duplicate prompt? Also, LLM does not need the history in the prompt, so just the fulltext or not”

What it is: L9 and L11 exist only to say “the abstract could not settle it”, which is our bookkeeping, not something the model needs. The rules and JSON block are otherwise duplicated verbatim.

Recommendation: Agreed. One prompt with an optional PARSED FULLTEXT block halves the outcome prompt surface and removes a class of drift where one copy is edited and the other is not. Do it together with D8.

D8 Move TITLE/ABSTRACT/FULLTEXT to the bottom of the prompt — L8–L11

“This should be at the bottom — both for caching and for instruction following”

What it is: Instructions currently sit after the paper text, so the longest, most variable block separates the model from its task.

Recommendation: Agreed on instruction-following grounds. The caching argument only pays if the static prefix clears the provider’s minimum cacheable prefix — worth checking against the actual prompt lengths before claiming it as a saving. Do with D7.

D9 Drop the L1 decision rules that restate the criteria — L1

“Do we think these add anything? They seem to restate criteria?”

What it is: Rules 1–4 restate the type definitions directly above them; only rule 5 (false_positive overrides) adds anything.

Recommendation: Agreed — keep rule 5, drop 1–4. Not applied because L1 already changed substantially in PR #89 and two edits to the same prompt in one pass makes any behaviour change impossible to attribute.

D10 L2 should return the target, not just a count — L2

“this is clearly nonsense — needs to return match/candidates if single, so that we don’t do the same extraction twice — and should also ask whether it is a replication unless LLM (rather than rule) has already confirmed that”

What it is: L2 shows the model the title, abstract, cited patterns and the full candidate list, then asks only “how many originals?” — and L3 then shows it the same material again to ask which one.

Recommendation: Agreed that this is wasteful. Two ways to fix it: have L2 also return the selection when it answers single_original, or fold L2 into L3 entirely and let one call return both. I would fold them. This is the largest change on the list — it restructures Stage 3 routing, so it wants to be its own PR.

D11 Ask for a candidate key, not a candidate number — L3/L6

“it would seem less risky to get an explicit key rather than a number (as smith2009 is less likely to be mismatched by llm than 3)”

What it is: The model returns selected_candidate_number, an index into a list we built. An off-by-one silently selects the wrong paper and nothing downstream can detect it.

Recommendation: Agreed, and the failure is invisible, which makes it worse than it looks. Use the OpenAlex ID or an author+year key that we can validate against the list we sent. Needs the response parsing to change with it.

D12 One role prompt, or none — all

“If we use roles (which likely does no harm, even if no longer recommended?), they should be uniform across prompts”

What it is: Roles vary: “an expert in scientific replication and reproducibility” (L1), “a research methodology expert” (L8–L11), “an expert in research methodology identifying ALL original studies” (L7), and none at all in L2, L4, L5.

Recommendation: Uniform or absent, either is defensible; mixed is not. Suggest picking one line and using it everywhere — the variation is historical, not designed.

D13 The one system message is wrong for most calls that send it — S1/S2

“Any reason to use multiple without dedicated validation? At most, we should have a default and then plumbing to supersede these individually? Also, is there value in a system message that overrides the prompt?”

What it is: There is only one system message, and S1 and S2 are the same string. But it is attached to every call_openai() and call_openrouter() — including the Stage 2 filter, the outcome coder and the reference screen, none of which identify original studies. Those calls are told “You are a research methodology expert that identifies original studies from replication papers” while being asked to do something else.

Recommendation: Recommended fix. Either make it neutral (“Always respond with valid JSON only.”) or pass a per-call system message. The current text is actively misleading on the majority of calls.

Does this input earn its place?

Blocks we add to prompts whose value is untested. Mostly settled by an experiment, not an argument.

D14 Does the cited author-year pattern block help? — L2, L3/L6

“Does this benefit an LLM? … again — does this help? If misparsed, might lead the LLM astray. If parsed correctly — trivial for LLM to spot?”

What it is: Both prompts inject regex-extracted author-year pairs alongside the abstract the model can already read. When the regex misfires, the model is handed a confident wrong hint.

Recommendation: Empirical, and cheap to settle: rerun a sample with the block removed and compare resolutions. Propose 200 rows that currently resolve via llm_cited_candidates. My prior matches yours — a modern model reads the citation off the abstract unaided.

D15 Is the title-pattern hint (F2) worth keeping? — F2

“Is this “hint” useful? I doubt it for modern LLMs given that the parts are in the prompt”

What it is: F2 tells the model that the title looks like “A Replication of X” and lists candidates matching X — both the title and the candidates are already in the prompt.

Recommendation: Agreed it is probably redundant. It also has a side effect worth fixing regardless: because F2 does not start with ⚠ FLoRA ANCHOR, F3 wraps it in “a human reviewer marked the previous answer as INCORRECT” — see D16. Suggest removing F2 and measuring.

D16 Delete the F3 validator-feedback wrapper — F3

“This seems value-free (and hard to include into a pipeline) — a human that identifies that the target is wrong should identify the correct target.”

What it is: Agreed on the principle, and the implementation has a concrete bug: the branch tests the combined note, so a bare title-pattern hint or any user comment is presented as “A human reviewer marked the previous answer as INCORRECT” even when there was no previous answer.

Recommendation: Recommend deleting F3. If a validator knows the target is wrong, the right output is the correct target, not a nudge. That removes the bug rather than fixing it.

D17 When does the FLoRA anchor (F1) fire at all? — F1

“why would this ever appear here?”

What it is: F1 fires when the FLoRA sheet already holds a manually verified original for this DOI (validated - changed/unchanged) that is missing from the candidate pool.

Recommendation: The sharper question is the one behind yours: if FLoRA has already verified the original, why is the row being re-extracted? Skipping those rows outright is simpler than anchoring the model toward an answer we already have.

D18 Do the phrase/cite paths need to stay separate? — Stage 2

“Unsure whether these need different paths as we need to decide for both whether they truly are replications/reproductions and what their target is? Consolidate into one path of potential candidates?”

What it is: “Phrase without a same-sentence cite” → needs_review/medium; “phrase + same-sentence cite” → replication/high. Both still need the same two questions answered downstream.

Recommendation: The split buys one thing: the high-confidence path skips the Stage 2 LLM. Whether that saving is worth a second code path depends on how often the rule path is right — which the filter_method breakdown can answer directly before deciding.

Truncation and the full-text budget

Where we spend tokens and what we throw away. D24 is the one with real money attached.

D19 Should the section snippets be truncated at all? — L3/L6

“I wonder if we should shorten this at all? Makes pipeline reporting odd, as these constants cannot effectively be validated … or if we want to cut off the longest tail, should we take start and end of sections (as plan for study is often at the end of the introduction)”

What it is: abstract[:700], intro[:600], methods[:400], html[:1000] — none of these numbers has a justification on record.

Recommendation: The start-and-end point is the good one: the sentence naming the replicated study usually sits at the end of the introduction, which is exactly what [:600] discards. Suggest first 400 + last 400 of intro, and treating the rest as measurable rather than settling it by argument.

D20 Send page ranges, not the whole PDF — L12

“does this make sense? Should at least limit the number of pages — but in most cases, first 5 plus ref heuristic below should be good?”

What it is: L12 uploads the entire PDF inline with no truncation, to extract a reference list.

Recommendation: Agreed. First ~5 pages plus the trailing-20% heuristic already used by L13 would cover nearly every layout at a fraction of the upload.

D21 The 45 MB skip should be a page subset, not a skip — L12

“why? Any size constraint? Would seem that this should be a page number limit (and that this might be circumvented by subsetting pages rather than skipping)?”

What it is: Papers over 45 MB are dropped silently — no reference extraction, no log line the pipeline surfaces.

Recommendation: Agreed, and it follows directly from D20: once pages are subset, size stops being the binding constraint. Large files are usually image-heavy scans, which are exactly the ones parsing already failed on.

D22 MEDIA_RESOLUTION_LOW when parsing already failed — L12

“does this make sense if PDF parsing fails? That seems to suggest that the PDF needs visual reading”

What it is: L12 only runs because text extraction produced nothing — which usually means a scan — and then asks the model to read it at reduced resolution.

Recommendation: Agreed, the two settings work against each other. Raise the resolution on this path. It fires rarely, so the cost is bounded.

D23 Is the image fallback (L13) redundant with L12? — L13

“any point in this if using Gemini? Doesn’t that read the PDF as images anyway?”

What it is: L13 renders pages to PNG and sends those; L12 sends the PDF and lets the model rasterise it.

Recommendation: Likely redundant, but they fire on different triggers — L12 when pdfminer found no text, L13 when it found text but no references. Worth checking how often L13 succeeds where L12 failed before removing it; the caches on disk can answer that without new API calls.

D24 Ask the expensive PDF call for everything at once — L12

“also, when doing such an expensive PDF call, get all information at once — i.e. also outcome, and confirmation of classification?”

What it is: Having paid to upload a whole paper, we ask only for its reference list, then pay again elsewhere for the outcome.

Recommendation: The best cost idea on the list. One call returning references + outcome + a classification check would remove a separate LLM pass on precisely the rows that are most expensive. Its own PR, and it interacts with D7/D10.

D25 Greyscale page rendering — L13

“is this more token efficient? Otherwise, why not keep color, e.g. given that links offer visual separation?”

What it is: Pages are rendered at 1.5× zoom in greyscale before upload.

Recommendation: Greyscale saves upload bandwidth, not tokens — image cost is charged by dimensions, so colour is close to free here. Suggest colour, for the reason you give.

Model configuration

Two inconsistencies in the provider chain; D26 is a probable live bug.

D26 max_tokens=1024 is too small for a reasoning model — S1/S2

“too little for reasoning model?”

What it is: call_openai sets max_completion_tokens=1024, which on gpt-5-mini includes hidden reasoning tokens. The same responses are asked for an outcome_phrase of up to ~1200 characters — roughly 300 tokens of visible output before anything else.

Recommendation: Recommended fix, and the most likely live bug on this list. A truncated response is not valid JSON, so it is indistinguishable from a parse failure and is retried rather than reported. Suggest 4096 and a log line when a response is cut off.

D27 Temperature is set on some providers and not others — S1/S2

“Is this a good idea? I remember that temperature 0 can be unstable — also, does it make sense when not set for the main models?”

What it is: Gemini sets temperature: 0.0, OpenRouter sets 0.0, OpenAI sets nothing and takes the default. So the fallback chain changes sampling behaviour mid-run.

Recommendation: The inconsistency is the real problem, not the value. Set it explicitly on all three or none — and decide which, so a row coded by the OpenAI leg is comparable to one coded by Gemini.

Raised after PR #89

Your comments from this afternoon. D32 is a live inconsistency PR #89 introduced.

D32 RRR is still hard-wired as multi-original in the rule classifier — run_extract.py:229

“I hope these are gone?”

What it is: Half gone, and the remaining half is the one that matters. PR #89 removed Registered Replication Report from the L2 and L7 prompts, but _MULTI_TITLE_RE in classify_match_type still matches registered replication report (and many labs, many analysts) on the title and returns multiple_original at high confidence — before the cache and before any LLM call. So for exactly the papers you flagged, the prompt change has no effect: the rule already decided. Verified: “Registered Replication Report: Finkel et al. (2002)” → multiple_original.

Recommendation: This is an inconsistency PR #89 created and I should have caught. The prompt now says RRRs are not a multi-target signal while the rule above it says they are, at high confidence. Recommend dropping registered\s+replication\s+report from _MULTI_TITLE_RE and letting those titles fall through to the LLM, where the abstract can decide. Many Labs and Many Analysts genuinely are multi-target and should stay. Say the word and I will send it as a one-line PR.

D33 “replications of N” fires on N experiments from one original — run_extract.py:243

“what does this mean? “we present 2 replications of smith (2009)” would obviously be single target”

What it is: Your exact example is safe — the pattern needs digits after “of”, and the count bound is 3 ≤ N < 1900, so 2 replications of Smith (2009) falls through to the LLM. But the sharper version of your point does fire: “We report replications of 5 experiments from Smith (2009)” → multiple_original, high. Five experiments, one original paper — routed to the multi pipeline and expanded into five rows.

Recommendation: The rule counts replications and assumes each has a distinct original. Recommend requiring the counted noun to be studies/findings/papers and excluding experiments, which within a single paper usually means Study 1…Study N of one original. Cheap to fix and testable against the rows the rule currently fires on.

D34 Exclude FLoRA-validated rows rather than anchoring them — F1

“these should not be run but excluded at the start — might want to use the pipeline to validate FLoRA content, but then run independently”

What it is: Agreed, and this is the same point as D17 arrived at from the other side. Today a validated FLoRA row is re-extracted with its known answer injected as a prompt note, which costs a full extraction and produces a result we cannot treat as independent evidence.

Recommendation: Recommend excluding them at the filter stage and deleting F1 with D17. If you later want the pipeline to audit FLoRA, that is a separate run with the anchor off — which is the only way the comparison means anything. Merging D17 and D34 into one decision: exclude, and drop F1.
