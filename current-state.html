FLoRA Extractor — current state

The codebase as it stands on 2026-08-06, at fix/current-state-findings @ 6a83f96 (working tree clean apart from this page; not yet merged to main). Mapped by three code-only survey agents that were barred from reading CLAUDE.md, docs/ or any earlier state page, so nothing here is inherited from the previous description. Every count was read off the artifact or produced by a command, never estimated. Test suite: 1217 passed, 6 skipped, 2 xfailed.

Operationally, the pipeline cannot be run end-to-end right now. Two blocks, both consequences of the screen moving into Stage 2:

  1. The Stage 2 → Stage 3 export gained six screen_* columns. The column list is hashed into schema_version, which is one of the six inputs to a release id — so every stored release is stale and export, screen and handoff all refuse against it. A fresh route over the 5.1M-row pool is required first.
  2. data/filtered.csv on disk predates that change (21 columns, no screen_verdict), so python -m extract.run_extract refuses to start against it — deliberately, rather than silently re-screening.

1 · What the pipeline is

Stage 1  search/           OpenAlex bulk-parquet snapshot scan (token-stem OR concept gate)
                           → survivor pool: flat zstd parquet, 2,232 files / 7.1 GB / 5,146,160 rows
                           → ledger-backed resume;  HF share via pool_sync

Stage 2  filter/engine/    16 JSON specs (10 live, 6 shadow) precedence-routed into piles
                           state: DuckDB (derived) + Supabase (claims/verdicts, authoritative)
                                  + release JSONs + HF blob archive
                           screen_expensive tier = THE screen (2 voters, G-softqual gate)
                           screen_cheap tier     = dormant by design, wired and tested
                           → handoff writes data/filtered.csv, atomically

Stage 3  extract/          reads the screen verdict off the row (does not re-screen)
                           → 7-rung resolution ladder → outcome coding (2 vocabularies)
                           → DOI verification → data/extracted.csv
                           sanity_check quarantines into 9 set-aside CSVs on every exit

Stage 4  validate/         Flask dashboard over CSVs, a parquet mirror and Supabase
                           The Supabase import runs from the separate flora-validation repo

The load-bearing design ideas are real in the code rather than aspirational: content-complete cache keys with model, effort and prompt version folded in; one model constant per question with provider dispatch on the id and no fallback; a transient failure never checkpointed as a definitive answer; claims as the only cross-machine mutual exclusion; a first-success ladder ordered by cost; and evidence written before the verdict that names it.

2 · Stage 1 — search/

Entry point. python -m search.run_search --scan; --scan is required and a bare invocation exits with usage, because a bare call must never start a 400+ GB read. Other flags: --survivor-pool, --snapshot-max-files, --force-gate. Pilot mode is gone — a sample scan is done by pointing FLORA_CACHE_DIR at a scratch directory, which moves the ledger and the pool together. python -m search.snapshot_scan is a read-only status view; python -m search.pool_sync --push|--pull|--check-access shares the pool through a private HF dataset repo.

The gate is two vectorised pyarrow arms, OR'd. The token arm runs a 15-alternative stem regex (replicat, reproduc, reanalys, … plus 追試 and 반복검증) over the title and over the raw inverted-index JSON string — which is precisely why only single-token stems are sound there, since key order in an inverted index is arbitrary and a phrase regex would match by accident. The concept arm tests membership of OpenAlex concepts C12590798 and C9893847, with a separate code path for struct-list and JSON-string concept shapes (the string path is anchored on the closing quote because RE2 has no lookbehind and a bare C9893847 also matches C98938470).

Resume is a per-partition transaction: ledger merging → pool file commit (.tmp → final) → ledger done. The ordering is explicit, so a crash can leave a partition unscanned but never scanned-without-its-pool. A read failure retries with counters and the temp file rolled back each attempt, so a retried partition is never double-counted; a terminal failure restores the previous ledger entry and records nothing as consumed. There is no dedup across partitions — a work updated twice sits in the pool twice, and Stage 2's first-writer-wins insert on (release, work_id) absorbs that.

Generation hygiene is now enforcing rather than advisory. A ledger naming a different gate fingerprint refuses to scan (--force-gate overrides and warns); a ledger that exists but will not parse is a hard error rather than a silently-empty fresh start, because the alternative is an unnoticed 725 GB rescan or a doubled pool. pool_sync --push refuses on a differing fingerprint or an unreadable remote manifest, commits the manifest first so an interruption cannot leave a large unfingerprinted pool, and proves write access by actually committing a preflight file (create_repo(exist_ok=True) succeeds for a read-only token). Pull still only warns on a mismatch.

Abstract retrieval (fetch_abstracts.py) is a library with no CLI; its consumer is filter/engine/backfill.py. Six sources are split into two pathways by cost. The bulk pathway (OpenAlex 50-id filter queries, Europe PMC 100-DOI searchPOST) runs first over every missing-abstract row; the targeted pathway (OSF, Semantic Scholar, CrossRef, Scopus last) then sees only what bulk left textless. OSF is the deliberate exception — it always sees the full worklist, because its registration template line is text two specs read and a Europe PMC abstract is not a substitute for it.

The transient-vs-definitive contract here is the strictest in the repo, and it holds: a per-item fetch returns ok / empty / transient / stop, and only empty is ever written — meaning the source answered and holds nothing. A 401/403 is stop, not empty, in all four gated sources, because auth is host-wide and one refusal would otherwise write a permanent "no abstract exists" for every DOI it touched. A whole-batch failure checkpoints nobody, and Europe PMC refuses a page where hitCount exceeds the records returned, since a truncated page is not an answer. Twenty-five consecutive transients stop a phase. The SQLite abstract store's row is the checkpoint.

3 · Stage 2 — filter/engine/

Entry points. python -m filter.engine with nine subcommands (specs, route, diagnose, export, screen, reconcile, handoff, worklist, status), plus three modules with their own argparse — backfill (abstracts → overlay chunk), supersede (validation lineage) and sizing (Postgres storage estimate). Those three are now named in the main CLI epilog. There is no verify subcommand any more; it went with the second regex backend.

The rule book

18 JSON files in filter/spec/, of which three are not specs (conventions.json, aliases.json, and holdout.json, which does not exist) — so 16 specs load, 10 live and 6 shadow. The 10 live are 7 discards and 3 admissions. Specs sort by (−precedence, id); the first non-shadow match wins; shadow specs are evaluated and recorded but can never claim a row.

Two policies are the engine's rather than any spec's: an unclaimed row becomes pending / no_filter_matched (a rule that did not fire has said nothing, not "keep"), and a screen-pile win on a row with an empty abstract is downgraded to pending / no_text — absence of evidence must not convert itself into a proceed. Discards are exempt, since structural rules do not read the abstract. A non-shadow discard must additionally carry a measurement at an autonomous level; heuristic alone is refused, though trusted remains self-certifying.

One regex engine. The Python-re evaluator and the sampling backend-equality verify command are gone. eval_spec_batch() (pyarrow/RE2) decides every match for every caller; the row-shaped eval_spec_rows() is a thin entry point that builds a one-row batch and calls it, so analysis scripts provably agree with routing. RE2 syntax is validated by asking pyarrow itself at spec-load time rather than by a hand-maintained list of banned constructs. Python re survives in exactly one place — match_evidence() asks it where a match sits, never whether, because it is the only engine in the process that reports a span; when the two disagree on a span the evidence falls back to naming the condition rather than inventing a phrase, and no row's pile depends on it.

Why that consolidation was worth doing. Before deleting the equality checker, it was run over 289,141 real pool rows and found a genuine disagreement: an abstract containing mojibake (toÂ apply) where the Â sits exactly where a trailing \b looks. Python's Unicode-aware \b saw a word character, ASCII RE2 did not, and the two backends returned different verdicts. The sampling verify — first batch of the first 200 files — was never going to prove that absent. Routing already ran on RE2, so no pile moved; the full routing table over 853,836 pool rows hashes identically before and after the change.

A release is a sha256 over exactly six inputs: pool-manifest hash, overlay hash, bundle hash (the 16 specs plus conventions, whitespace-sensitive), engine version, alias release, and CSV schema hash. Every consumer re-checks the binding and there is no override — which is exactly why adding the screen columns invalidated every stored release.

The tiers

Dry run is the default and needs no state authority at all; it prints row counts, per-row token quantiles and a price estimate from a constant table that sits next to its only reader. --run claims the whole batch in one RPC before the first voter — all-or-nothing under a per-tier advisory lock, so a conflict ends the run with nothing spent. Budget is checked per work inside the worker, and an exhausted budget fails the claim while keeping the verdicts already written, because the budget did not un-spend them.

Verdicts are keyed to a screening generation — a hash of the sorted voter models plus the classify prompt version, the same ingredients as the LLM cache key, carried in the claim's metadata. Change a voter or the prompt and old verdicts stop counting: those works become claimable again and stop steering the handoff. Within a generation, verdicts are read across all releases deliberately, so a pure re-route does not unask a voter. Rows predating the field are grandfathered on their recorded model set. Models are sorted, so swapping voter slots is not a new generation.

The expensive tier is the screen, and now the only one: classify_replication() + screen_gate() run here and nowhere else. It writes one verdict row per voter plus a blob holding the votes, the gate and the full screen dict. On read, the gate and record type are recomputed from the stored votes rather than trusting a stored summary, and the votes are re-sorted into call order because a split is broken by taking the first qualifying voter.

The cheap tier is dormant by design, and this is deliberate rather than neglect. The reason it is inert is singular and structural: all three screen_cheap specs are shadow, so nothing routes to the pile and a claim finds nothing. Three further facts shape what waking it would mean, but are not themselves the cause — its verdicts may only discard, never admit (the handoff counts only expensive-tier verdicts as deciding, which is the intended semantics); its curated-source bypass arm can never fire, because the pool schema carries no source column, so that safety net is currently absent; and its two OpenRouter voter models have no key configured on this machine, which is local state rather than a property of the codebase. The apparatus — voters, prices, the prescreen_discard set-aside, --rescreen's reopening — stays wired and tested, so promoting a spec is the only code change needed; a run would additionally need an OpenRouter key and, before it may discard anything, the re-measurement described under §7.

The handoff

handoff writes data/filtered.csv from the two screen piles, expensive first so a --limited Stage 3 run meets the strongest signal first. Screened-only is the default: a row is dropped if a live tier verdict discarded it, and skipped if it was never screened. It writes to a sibling .tmp and os.replace()s it in, so the file is either the old handoff or the new one and never half of either. --as-routed is the only mode that works without Supabase, and it is also the only way a row can arrive at Stage 3 with blank screen columns.

4 · Stage 3 — extract/

The screen is not here any more. Stage 3 reads the six columns and rebuilds the verdict dict in-process, so the downstream consumers — record typing, the reference-screen gate, the title-search gate — are unchanged and no second opinion is bought. Three cases are distinguished deliberately: a missing column is a startup refusal naming the two commands that fix it (one loud failure beats a million silent target_pendings); a blank value writes that row target_pending with a note, which is the same ending an incomplete screen always had; and --screen-here is the explicit opt-in that screens in Stage 3 for verdictless rows, requiring both voters' API keys at startup. Nothing silently re-screens. The one thing the CSV cannot round-trip is per-voter categories and reasoning; anything needing those must go back to Postgres.

Row lifecycle. filtered.csv is read in 50k chunks in two passes (abstract-bearing rows first) → a six-step skip chain (FLoRA lists → validated-skip → resumed → already-extracted → false_positive → reproduction flags) → a thread pool (EXTRACT_WORKERS=4, back-pressure at 2× in flight, one lock per paper's write set) → screen → ladder → guard → outcome → finalise → append. The finally: runs the token summary, the new OpenAlex search-query summary, sanity_check and the dashboard refresh even on Ctrl-C or a budget stop, and budget/quota exceptions win over incidental errors in reporting.

The ladder returns at its first success, ordered by cost: candidates re-query → title-pattern match → rule-based citation/candidate match → abstract LLM (only where author-year patterns exist) → reference-list LLM → pre-PDF title search → PDF acquisition (11 tiers) → six-parser parse and scoring → full-text LLM. A content-free OpenAlex XML shell is not a document — it ends the row at no_fulltext_available, and that check is now applied consistently by the parse-cache probe as well as the ladder.

The withhold gate holds a deterministic pick back whenever the paper's own text does not rule out a second target, and restores it at every exit where nothing that could enumerate targets has spoken — including after a full-text call that named nothing or named the same work. A provider failure is not that answer, so it does not restore. llm_title_search stays outside the resolved set at roughly 50% precision: never outcome-coded, never imported, set aside for human confirmation. It is also the ladder's dominant OpenAlex cost, since a free-text search is billed at 10× a filter query, which is the second reason it sits last.

Outcome coding runs only on a resolved link. Replications use the eight-value vocabulary; reproductions are coded on two independent axes (computation, robustness), each with its own escape and quote, and escalation to full text is per axis, with the escalated call replacing both. Naming the other vocabulary re-codes the row once and corrects its type. An api_error is never cached, and neither is an abstract verdict returned only because the full-text escalation itself failed.

Verification, and what a resume costs

Every written row's doi_o is checked against the metadata it actually points at. The important recent change is a third outcome: unverifiable. A partial outage — CrossRef down, OpenAlex reachable but holding nothing — used to look identical to "no replacement exists", which writes mismatch, which deletes the row's doi_o. Now a source that never answered yields a falsy sentinel that is never cached, the row keeps its DOI, and its verification records api_error. Both verification caches were key-versioned rather than declared equivalent, because the meaning of a stored "no match" genuinely changed and old entries must miss.

A resume no longer re-verifies rows whose verification is settled; api_error and blank are retried, which is the point of the sentinel. Carried rows still get the free half (year normalisation, work-id fill, control characters). Worth stating honestly: with a warm local cache (3,675 entries) the recurring cost this avoids was disk reads rather than HTTP — the real bill lands on a cold cache, a fresh machine or CI, and grows with extracted.csv.

The four known in-process ways a resume could lose rows are closed, after a documented 76-row loss:

  1. The header is written up front, on both --fresh and resume, so no later write can be the one that truncates.
  2. Every carried row is written; a row whose finalisation raises is written as-is rather than dropped.
  3. An exception mid-carry flushes the remaining carried rows before unwinding — which also closes a Ctrl-C window that existed even with no bug at all.
  4. Pending papers the run never handled are written back unchanged in the finally.

What that does not establish is an absolute guarantee. The output is still rewritten in place: the header write truncates the file before the carried rows go back, and there is no temp-file-plus-atomic-replace transaction around the Stage 3 output as a whole. A SIGKILL, host loss or disk failure inside that window still leaves a header-only or partial file. Closing that properly is listed in §7.

Set-asides

sanity_check runs on every exit and files rows first-match-wins into nine CSVs across twelve buckets. Resume treats every destination as settled except the two a run always redoes — target_pending.csv and api_error.csv, the latter because an api_error row carries no verdict and a transient failure must never become permanent. --rescreen reopens only the three screening files, and now means reopen rather than re-screen: it lets a new Stage 2 screening generation re-admit those rows. Set-asides live beside the CSV they came from, so a --extracted-test run can no longer file a discard into the production set-asides and thereby settle a paper the production run never processed.

5 · Cross-cutting machinery

Models, providers, caching

Seven model constants live in config.py, each named for the question it answers, each with one call site and no os.getenv. The provider follows the id shape — a "/" means OpenRouter, a leading gemini means Google, anything else OpenAI — and an import-time guard pins the PDF model to Gemini, whose document calls have no OpenAI-compatible form. There is no fallback ladder: when a provider fails, the call fails. Effort is a per-call-site argument rather than a property inferred from the model id, which matters because three of the constants are currently the same string.

A cache key names everything the answer depends on: prompt version, model-with-effort, and the inputs sent. prompt_version() is an AST-transitive hash of the builder and every constant it splices, so editing a shared fragment invalidates exactly its users and nothing needs registering. The declared-equivalence mechanism is the one opt-in exception, used in two places today, and it is worth knowing which is which:

  • The classify voter component carries two legacy labels, so cache entries written before the key named an effort are still found, re-stored under the current key with a migration note, and left in place for other checkouts. The equivalence is rebuilt from the current prompt, so it self-expires the moment anything else moves.
  • The retired provider system message is still hashed under its original part name although it is now sent to nobody. This is a deliberate project-wide equivalence: dropping it from the hash would move every prompt version at once and orphan every LLM cache the project holds. All seven prompt versions are byte-identical to what they were, and the constant carries a warning that editing the string re-buys every cached answer.

The two versioned doi_verify keys are the opposite decision made on purpose, and are described above: there the meaning of a cached answer changed, so old entries must miss.

cache_sync shares seven cache parts plus the abstract SQLite through the same private HF repo. The correctness argument is that content-complete keys make a differing checkout miss rather than mis-read. A pull never overwrites a local file; a push now refuses to replace a remote shard that holds entries the local one lacks (--force overrides), which closes the hole where a partial cache could shrink the shared shard and pullers would then record the smaller digest as current.

Cost and rate

Every LLM call records input and output tokens per day, provider and model, recorded before the truncation early-return since a response cut off at the cap is the most expensive shape there is. Only OpenAI is hard-capped. OpenAlex is metered per request against a daily budget with rotation on exhaustion, and a run now prints how many free-text searches it issued — the 10× tier. Uninstrumented still: OpenAlex content downloads (the 100× tier), plain filter queries, and every non-OpenAlex HTTP source. throttle() is one reservation queue per service so N worker threads share one rate; one CrossRef path in doi_verify still sleeps after its request instead of reserving before it.

Tests

1,217 pass in about 12 seconds. Five autouse fixtures make the isolation real rather than conventional: sockets raise, backoff sleeps are nulled, and the token store and abstract store are redirected to temp directories. Live tests sit behind TEST_LIVE_API. There is no pytest config file, no CI job that runs the suite, and TEST_LIVE_API is a global switch rather than a per-directory one — so setting it would lift the socket block for all 1,200-odd mocked tests at once.

6 · Where the code is weak

These are current defects, ranked. Everything the 2026-08-05 review raised has been fixed, dissolved, or is listed below with its reason for still being open.

W1 · Every stored release is stale, so nothing can be handed off. blocks the pipeline

Adding SCREEN_COLS moved schema_version, one of the six release inputs. All six stored releases were routed under the old bundle and schema hashes, and export, screen and handoff correctly refuse against them. This is the binding mechanism working as designed, but the consequence is a required route re-run over 5.1M rows before Stage 3 can be fed again. Verdicts are not lost — they are read across releases within a generation.

W2 · Four stored releases record provenance that names nothing. cause fixed

The release id's pool input used to be a hash of the scan ledger — one machine's account of a scan — rather than of the pool that routing actually consumes. A machine that obtained the pool by pulling has no ledger, and a missing ledger did not raise; it yielded an empty one, whose hash is the SHA-256 of the empty string. Four of the six stored releases still carry that value, e3b0c442….

The cause is fixed: the release now hashes the pool directory itself — every parquet file's name, size and row count, read from the footers (0.15 s over the real 2,232-file pool), plus the search gate those rows were admitted under, which the pool carries in a _pool_provenance.json sidecar written by the scan and by pool_sync --pull. Hashing the reading checkout's own gate would have re-created the mislabelling in another form, so the recorded value is the one that counts and a pool shared between machines fingerprints identically on both. The sidecar also names the file count that completes the pool, so an interrupted pull is unmanifested rather than a plausible hash of a fraction of the corpus; every pool that predates it — including the local one — routes with its gate recorded as explicitly unknown and a loud warning naming --stamp-pool. The scan ledger goes back to being purely a resume artifact, and the pushed remote manifest keeps its frozen format so pools already on Hugging Face still compare equal. The stale ids remain on disk until the next route re-mints them, which is the only reason this is still listed.

W3 · A stranded claim is permanent and silent.

There is no expires_at, heartbeat, TTL or reaper. A claim is released in exactly one place, inside the run's completion path, so a SIGKILL or a lost host leaves it active forever — and because the next batch subtracts claimed works, those rows are quietly excluded from every future run rather than raising. No CLI exposes a release; the only remedy is hand SQL.

W4 · A transient read failure can erase the spend record.

token_usage._read_all() returns {} on any OSError. The daily OpenAI budget then reads as unspent, and the next record() read-modify-writes from that empty dict — destroying the accumulated multi-day record. It is the one place where a transient failure is promoted to a definitive fact about money.

W5 · The dashboard exposes unauthenticated endpoints that can spend money.

The /batch blueprint registers on any run where FLORA_READONLY is unset — which is the default locally — and its POST endpoints call the extraction ladder directly, making live OpenAlex, LLM and PDF calls and writing CSVs. Nothing authenticates them. They are inert today only because the input CSVs they read do not exist, which is an accident of the filesystem rather than a control. On a dashboard described elsewhere as read-only, that is the wrong thing to be relying on: either delete the blueprint or gate it deliberately.

W6 · The dashboard's numbers are stale, and Stage 2 never refreshes them.

stats.json reports 2,582,749 filtered rows against 1,614 on disk, and 1,813 extracted against 285, because nothing under filter/ ever calls the refresh and the presence of the cached key suppresses the recompute. The shipped template also still instructs users to run python -m filter.run_filter, a module that no longer exists.

W7 · Postgres schema gaps.

The hottest read — verdicts by tier with offset paging — has no supporting index, and mark_uploaded PATCHes on an unindexed hash repeatedly per run. There is no migration-tracking table or runner, and 0001 was retro-edited in place, so 0003 is a no-op against a fresh database and nothing detects the checksum change. engine_verdicts.prompt_hash is written only by the cheap tier, so every expensive-tier verdict — the tier that actually gates Stage 3 — stores an empty string. Several Python-side invariants have no DB constraint, including tier spelling, which a typo makes silently invisible.

W8 · Provider asymmetries that remain. Gemini retries twice per key at a flat 3 s while OpenAI and OpenRouter retry three times at 1 s/2 s; Gemini's output cap is a hardcoded 8192 against 4096 elsewhere, so the same logical call truncates at different points; only OpenAI is budget-checked; only Gemini prints to stdout. Token recording, the retry loop's existence and the absence of a system message are now uniform.

W9 · Self-contradicting and drifted surfaces — including inside the reworked code. link_original.py still narrates the previous architecture in its docstrings: that Stage 3 votes at its own front door, an incomplete-screen and disagreement flow that no longer exists, seven PDF sources where there are eleven, and a title-search rung running after the PDF stage rather than before it. Those are the most dangerous stale passages in the repo, because they sit in the file a reader trusts most about the ladder. pool_reader.py's docstrings say an overlay "fills and never replaces" while the code — and its test, and an inline comment arguing for it — replace always. docs/cli-reference.md still documents a Stage 1 CLI with nine flags that no longer exist. Three spec descriptions name a rule family that was renamed. CLAUDE.md still lists the deleted shared/csv_index.py and a --rebuild-index flag, and still says filtered.csv exceeds 1M rows. Eight value-set constants in schema.py validate nothing.

Deliberate trade-offs, so they are not re-litigated as bugs

  • The frozen system-message salt. An independent review flagged that one cache key now names two different request shapes — an answer produced with the guard is reused for a request without it. That is the accepted cost of not re-buying every cached answer for a change judged answer-preserving; it is documented at the constant.
  • The cheap tier stays dormant rather than being deleted, because its evidence needs re-measuring on this distribution before it can discard, and the apparatus is cheaper to keep wired than to rebuild.
  • llm_title_search stays in the ladder despite ~50% precision, because it is quarantined rather than trusted, and it is the only rung that can resolve a DOI-less reference.
  • Reading verdicts across releases is intentional: a re-route must not unask a voter. The generation hash is what stops that from becoming staleness.

7 · Remaining work

Before the pipeline runs again

  1. Re-route and re-hand-off (W1). route over the 5.1M-row pool, then screen --tier screen_expensive --run, then handoff. Existing verdicts survive the new release — they are read across releases within a generation — so the cost is the routing pass, not the screening. Until this runs, Stage 3 has no valid input. The pool-provenance definition was deliberately corrected before this route rather than after (W2): the route is what mints release ids, so folding the change in costs nothing, while deferring it would have meant a second 5.1M-row pass.
  2. Decide the fate of /batch (W5). It is the open defect where the current safety rests on a missing file rather than on a control.
